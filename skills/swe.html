The senior bar

What separates a senior answer from a mid-level one in this area.

  • States the invariant and the complexity before writing code, then tests the edge cases unprompted (empty input, ties, duplicates, overflow of memory rather than of integers)
  • Explains performance from the mechanism (GIL, copies, cache misses, queueing, network round trips) and measures before changing anything
  • Designs for failure by default, so every remote call has a timeout, a retry policy, an idempotency story and a backpressure path
  • Gives numbers in system design (QPS, bytes, p99 budget, cost) and picks the simplest design that meets them, then says what breaks at 10x
  • Treats ML code as software with unit tests on transforms and losses, golden tests on a frozen checkpoint, a tiny end-to-end run in CI, and tolerance bands instead of exact equality
  • Uses coding agents with a verification loop and stays accountable for the diff, and can say where generated code typically fails

coreconceptMLE AI RE What is the GIL, and what does it mean concretely for a PyTorch data loader and for a Python model server?

The GIL is a lock in CPython that lets only one thread execute Python bytecode at a time. Threads still help when the work releases the lock: blocking I/O, and C extensions that drop it during long calls (NumPy on large arrays, PyTorch operators, most compression and many image-decoding libraries). Pure-Python CPU work (per-sample augmentation logic, JSON parsing, a tokenizer written in Python) gets no speed-up from threads.

Data loading. DataLoader(num_workers=N) uses worker processes for this reason. The costs are those of processes:

  • Batches cross a process boundary (pickled, tensors through shared memory).
  • Each worker holds the dataset object. With fork the pages start shared, but reference-count updates write to them, so a large Python list of objects is gradually copied into every worker. Store samples in NumPy or Arrow buffers instead.
  • Worker start-up is paid every epoch unless persistent_workers=True.

Serving. One Python process runs Python code on one core. The usual designs:

  • Several worker processes behind a load balancer; each loads its own copy of the model, which multiplies GPU memory.
  • One model process with dynamic batching, where the forward pass runs in C++/CUDA with the GIL released, and Python only orchestrates.
  • Move CPU-heavy pre-processing out of Python: Rust tokenizers, a C++ or dedicated inference server.

CPU-bound code inside an async handler is worse than slow: it blocks the event loop for every request.

Version note: CPython 3.13 added an experimental free-threaded build (PEP 703) and 3.14 made it officially supported but still optional. Single-thread overhead and extension support are the practical limits, so check each library before relying on it.

Follow-ups

  • Why does a thread pool speed up downloading images but not resizing them in pure Python?
  • Why can the memory of DataLoader workers grow during an epoch even when nothing leaks?
seniordebuggingMLE AI RE A preprocessing job over a 200 GB JSONL file is killed for running out of memory. Explain enough of Python’s memory behaviour to find the cause and fix it.

Something is materialising the data. Look for readlines(), list(...), sorted(...), json.load of the whole file, a list that accumulates results, or a DataFrame built from Python objects.

Why Python objects are expensive. Everything is a heap object with a header. On 64-bit CPython an int is 28 bytes, a float 24, an empty str about 50, an empty dict 64, and a list stores 8-byte pointers to its elements. A list of \(10^8\) floats costs about \((8 + 24) \times 10^8 = 3.2\) GB against 0.8 GB as a float64 array. A list of dicts per record is the worst case.

How memory is released. Reference counting frees an object when its count reaches zero; the cyclic garbage collector handles reference cycles later. Freed memory goes back to CPython’s allocator and not necessarily to the OS, so RSS can stay near its peak. Hidden references keep objects alive: a global cache, a closure, a stored traceback, a list of losses that still hold a graph.

Fixes.

  • Stream with generators: for line in f reads lazily; a generator pipeline (parse(filter(read(f)))) holds one record at a time. Generators are single-pass, and their exceptions surface at iteration time, not at creation.
  • Process in bounded chunks (itertools.islice, or itertools.batched from 3.12) and write each chunk out, for example to partitioned Parquet.
  • Columnar storage for what must stay in memory: NumPy, Arrow, __slots__ or dataclass(slots=True) for small records.
  • Shard the file and run one process per shard; np.memmap or Arrow memory mapping for random access.
  • Know which operations copy: NumPy basic slicing returns a view, boolean and fancy indexing copy, and so does most pandas filtering.

Measure with tracemalloc or memray, and peak RSS with /usr/bin/time -v. sys.getsizeof is shallow and undercounts containers.

Follow-ups

  • What is the difference between a generator expression and a list comprehension at run time?
  • RSS does not drop after del big_list. Is that a leak?
corecodingMLE AI RE Compute all pairwise squared Euclidean distances between X of shape (n, d) and Y of shape (m, d) without Python loops. What are the memory and numerical pitfalls? 
import numpy as np

def pairwise_sq_dists(X: np.ndarray, Y: np.ndarray) -> np.ndarray:
    # ||x - y||^2 = ||x||^2 + ||y||^2 - 2 x.y   -> (n, m)
    x2 = np.einsum("ij,ij->i", X, X)[:, None]     # (n, 1)
    y2 = np.einsum("ij,ij->i", Y, Y)[None, :]     # (1, m)
    d2 = x2 + y2 - 2.0 * (X @ Y.T)                # one BLAS matmul
    np.maximum(d2, 0.0, out=d2)                   # clamp rounding error
    return d2

Why not plain broadcasting: ((X[:, None, :] - Y[None, :, :]) ** 2).sum(-1) builds an \((n, m, d)\) temporary. With \(n = m = 10^4\), \(d = 768\) in float32 that is \(10^8 \times 768 \times 4\) bytes, about 307 GB. The expanded form needs only the \((n, m)\) output, 400 MB.

Pitfalls:

  • Cancellation: for near-identical points the three terms nearly cancel and the result can be slightly negative, which becomes NaN under sqrt. Clamp at zero, and use float64 if small distances matter.
  • Even \((n, m)\) may not fit: chunk over rows of X and reduce each chunk (top-k, min) before moving on.
  • For top-k per row use np.argpartition(d2, k, axis=1)[:, :k], \(O(m)\) per row, and sort only those \(k\).
  • Shape discipline: keep [:, None] and [None, :] explicit and assert the output shape.

Why vectorised code is fast: the loop runs in compiled code over contiguous typed memory, with SIMD and multi-threaded BLAS, and without creating a Python object per element. The gain over a Python loop is typically one to two orders of magnitude. It stops paying when the expression creates many large temporaries, since memory bandwidth then dominates; use in-place operations, numexpr, Numba, or move to the GPU (torch.cdist).

Follow-ups

  • Rewrite it for cosine similarity. What must be true of the inputs?
  • When is a Python loop over chunks faster than a single vectorised expression?

seniordesignMLE AI RE How do you test ML code, given that training has no obvious expected output?

Split the code into parts that do have an expected output, and test stochastic parts through invariants and tolerances.

  1. Unit tests on deterministic pieces. Transforms, tokenisation, collation, masks, metrics, and losses against a hand-computed case or a slow reference implementation. Assert shapes and dtypes.
  2. Invariance tests. Padding a sequence, or batching it with others, must not change its output. With a causal mask, changing token \(t+1\) must not change the output at \(t\). Permuting set-valued inputs must not matter.
  3. Numerical tests. torch.autograd.gradcheck in float64 for custom autograd code. Compare with torch.testing.assert_close and a tolerance, never with exact equality.
  4. Tiny end-to-end run (seconds, on CPU, in CI). Overfit one batch to near-zero loss. Initial loss is about \(\ln C\) for a \(C\)-class softmax. One optimiser step changes every trainable parameter and no frozen one. Save, load and get the same outputs. Resuming from a checkpoint matches an uninterrupted run.
  5. Golden tests. A frozen checkpoint and fixed inputs produce stored outputs within tolerance. This catches silent changes in preprocessing, tokenizer versions and post-processing. Updating a golden file is a reviewed change with a stated reason.
  6. Data tests. Schema, ranges, null rates, label distribution, no id overlap between train and test, and a parity test that sends the same raw record through the offline and online feature paths.
  7. LLM applications. Stub the model in unit tests (record and replay), and run a fixed evaluation set with pass thresholds as a slower gate.

Determinism. Seed Python, NumPy and PyTorch, seed DataLoader workers and pass a generator, and use torch.use_deterministic_algorithms(True). Results still differ across GPU models, library versions and thread counts, so regression tests use bands, not bit equality.

What not to do: assert a metric from a stochastic training run to three decimals, or put hour-long tests on every pull request.

Follow-ups

  • Which bug does the “overfit one batch” test catch that unit tests miss?
  • A golden test fails after a dependency upgrade with differences of 1e-4. What do you do?
staffdesignMLE AI What does CI/CD look like for a model, as opposed to a stateless service? What gates a model release?

A service release is determined by code. A model release is determined by code, data, configuration, random seed and environment, and its quality is statistical. So the pipeline versions more things and the gates are comparisons with noise bands.

Identity. A model artifact is traceable to a code commit, a data snapshot id, a config, a seed and a container image. If any is missing, the model cannot be reproduced or audited.

On every pull request (minutes). Lint and type check, unit tests, the tiny training smoke test, golden inference test, image build.

On merge or nightly (hours). Train (full or reduced), then evaluate on frozen sets and compare with the production baseline.

Release gates.

  • Primary offline metric not worse than baseline beyond the noise floor. Measure the floor by re-running the baseline with different seeds.
  • No regression on protected slices; calibration within bounds.
  • p99 latency, memory and cost per request measured on the target hardware.
  • Interface compatibility with serving: feature list, tokenizer hash, pre- and post-processing versions.
  • For LLM systems: safety and regression suites. Prompts and configuration go through the same gates, because a prompt change is a model change.

Delivery. A registry with stages; shadow traffic, then a canary of a few percent, then an A/B test, then full rollout. Automatic rollback on SLO or guardrail breach, with the previous model kept deployable.

Hard parts.

  • Flaky evaluations: a gate inside the noise blocks good changes and passes bad ones.
  • Evaluation sets go stale and get overfitted by repeated use; refresh them and keep a held-back set.
  • GPU cost of CI: tier the tests, and cache data and checkpoints.
  • CI cannot see drift; that is monitoring’s job.

Review norms. Reviewers of ML changes check split hygiene, leakage, metric code and whether the comparison is fair, not only style. Experiment configs are committed, so results can be re-run.

Follow-ups

  • How do you set the tolerance of a metric gate?
  • Who owns the evaluation set, and how do you stop the team overfitting to it?

coreconceptMLE AI RE Give me your structure for a 45-minute system design interview. Where do senior candidates lose points?

A fixed order, with rough timings:

  1. Requirements (5 min). The two or three core flows, what is out of scope, and non-functional targets as numbers: QPS, p99 latency, data volume, availability, consistency, cost.
  2. Estimates (3 min). A day has about \(10^5\) seconds, so \(10^9\) requests per day is roughly 12,000 QPS on average; plan for a peak of two to three times that. Storage is records x size x retention. The estimates decide whether one machine, one database or a sharded fleet is needed.
  3. API and data model (5 min). Endpoints, entities, keys and access patterns; the access patterns choose the store.
  4. High-level design (10 min). Client, load balancer, stateless services, storage, cache, queue. Trace one read and one write through the diagram.
  5. Deep dive (15 min). One or two hard parts: the hot path, the consistency problem, the scaling bottleneck. Offer candidates and let the interviewer pick.
  6. Failure and operations (5 min). What happens when each component dies, overload behaviour, monitoring, rollout, cost.
  7. Wrap-up. Trade-offs taken, and what changes at 10x.

Where points are lost:

  • Drawing boxes before asking for numbers.
  • Naming technologies instead of requirements (“Kafka” instead of “a durable log, because two consumers need replay”).
  • Presenting one design with no alternative and no stated trade-off.
  • Waiting to be led. At senior level the candidate drives and checks in.
  • Designing for scale the requirements do not ask for.
  • No write path, no data model, no failure story.
  • For ML candidates: all model and no system, or the reverse.

Useful magnitudes: a main-memory reference is about 100 ns, an SSD random read about 100 microseconds, a round trip inside a datacentre about 0.5 ms, across continents 100 to 150 ms.

Follow-ups

  • How do you decide how deep to go on a component the interviewer has not asked about?
  • Estimate the storage for one year of request logs for the system you just described.
staffdesignMLE AI Design a durable execution service for long-running agent or batch-inference jobs: steps take minutes to hours, workers crash, and steps call external tools with side effects.

Requirements. Submit, cancel and inspect jobs; a job survives worker and orchestrator crashes and resumes without redoing completed steps; every step runs at least once with an idempotent effect; timeouts and retries per step. Assume tens of thousands of concurrent jobs.

Core idea. Persist progress as an append-only event history per job (step scheduled, started, completed with its result). Workers are stateless; the orchestrator’s state can always be rebuilt by replaying the history. Workflow engines such as Temporal follow this model.

Components.

  • API and a transactional metadata store (jobs, steps, history).
  • Task queues with leases: a worker claims a step, heartbeats to extend the lease, and the step is redelivered if the lease expires.
  • Timer service for retries, timeouts and scheduled wake-ups.
  • Blob store for large inputs and outputs; the history holds references.

Semantics.

  • Lease expiry means redelivery, so steps are at-least-once. Each step passes a stable idempotency key (job id plus step id) to external tools.
  • Completing a step and enqueueing the next one must be atomic: write both in one transaction and publish from an outbox table, otherwise a crash between them strands the job.
  • A worker that lost its lease may still be running. Give each claim a fencing token and reject completions that carry a stale one.
  • On replay, orchestration code must take the same decisions. Model calls, tool results, clock reads and random numbers are recorded as step results and read back, never re-executed.

Long steps. Heartbeats carry a progress checkpoint (for example the batch offset), so a retry resumes mid-step. GPU pre-emption is handled the same way.

Failure policy. Per-step backoff and attempt limits, non-retryable error classes, a dead-letter state for human intervention, and compensation steps (a saga) to undo earlier side effects.

Scale and fairness. Partition history by job id; separate queues per tenant and priority; admission control at submit.

Operations. A per-job timeline, detection of jobs with no heartbeat, cost per job.

Trade-offs. Adopting an existing engine is usually right. Histories grow without bound for very long jobs, so snapshot and truncate. A DAG scheduler such as Airflow recovers at task granularity and suits batch pipelines, not interactive agents.

Follow-ups

  • A step charged a customer and the worker died before recording completion. What happens next?
  • Why must LLM calls be recorded rather than re-run on replay?

coreconceptMLE AI RE A Python training or serving process is slow. Which profilers do you reach for, in what order, and what does each one tell you?

Measure coarse to fine, and change one thing at a time.

  1. Stage timing and system view. Wall-clock per stage (data, forward, backward, optimiser; or queue wait, preprocessing, model, post-processing). nvidia-smi for GPU utilisation and memory, htop for per-core CPU, iostat for disks. This usually identifies which stage to profile.
  2. py-spy. A sampling profiler that attaches to a running process with no code change: py-spy dump --pid prints every thread’s stack (the tool for a hung job), py-spy top is a live view, py-spy record -o out.svg --pid writes a flame graph. --native includes C-extension frames and --subprocesses follows workers. Overhead is low enough for production.
  3. cProfile. Deterministic tracing with call counts and cumulative time per function. Its overhead is large and uneven (it inflates code that makes many small calls), so use it offline. line_profiler gives line-level detail in one hot function.
  4. torch.profiler. Per-operator CPU and CUDA time, memory and input shapes, with a trace export. Sort by CUDA time to find the expensive operators, and look for unexpected CPU-GPU copies.
  5. System level. perf for native code, strace -c for system calls, tracemalloc or memray for Python memory, torch.cuda.memory_summary() for GPU memory.

Reading a flame graph. Width is the share of samples, not time order; height is stack depth. Look for wide plateaus. An on-CPU profile hides waiting (I/O, locks, a starved GPU); use a wall-clock mode when the process is slow but not busy.

GPU timing. CUDA calls are asynchronous, so a timer around a GPU operation measures only the launch. Call torch.cuda.synchronize() before reading the clock, and discard warm-up iterations (lazy initialisation, cuDNN algorithm search, compilation).

Expectation. Amdahl’s law bounds the gain: speeding a fraction \(p\) of the run time by a factor \(s\) gives \(1 / ((1 - p) + p/s)\) overall.

Follow-ups

  • py-spy shows most samples in a queue.get call. What does that mean?
  • Why can cProfile point you at the wrong function?
seniordebuggingMLE RE GPU utilisation during training sits at 30 to 40% and fluctuates. How do you confirm that the input pipeline is the bottleneck, and how do you fix it?

Confirm with two experiments.

  • Train on one cached batch in a loop, with no loader. If throughput jumps and utilisation goes to nearly 100%, the GPU was starved.
  • Iterate the loader alone, with no model, and measure samples per second. Compare with the model’s maximum from the first experiment. The lower number is the bottleneck.

Also split each step into data-wait time and compute time (synchronise before reading the clock). A large data-wait share means starvation.

Rule out other causes of low utilisation. A .item(), .cpu() or print every step forcing a sync; logging or checkpointing in the loop; metrics computed on the CPU; a model or batch so small that Python and kernel-launch overhead dominate; in distributed training, ranks waiting for the slowest one.

Locate the cause inside the loader.

  • All worker cores at 100%: CPU-bound (decode, augmentation, tokenisation). py-spy dump on a worker shows where.
  • Cores idle with high I/O wait: storage- or network-bound.
  • The main process busy while workers are idle: collation or inter-process transfer.

Fix by cause.

  • CPU-bound: more num_workers up to the physical cores (watch RAM), persistent_workers=True, a larger prefetch_factor; move work offline (pre-tokenise, pre-resize, store decoded arrays); decode or augment on the GPU in batches.
  • I/O-bound: pack millions of small files into shards (tar/WebDataset, Parquet, LMDB) for sequential reads; cache on local NVMe; read in parallel.
  • Transfer: pin_memory=True with .to(device, non_blocking=True); return tensors or arrays from workers, not Python objects.
  • Variable-length data: bucket by length so batches are not padded to the longest sample.

Sizing. The loader must match the model’s throughput. If the GPUs consume 2,000 images per second and one core decodes and augments on the order of 100 to 200 per second (measure it), the job needs 10 to 20 cores for data alone.

Re-profile after each fix; the bottleneck moves.

Follow-ups

  • Utilisation is 100% but throughput is still low. What now?
  • Why can increasing num_workers make things slower?
seniordebuggingMLE AI After a deploy, the p99 latency of a Python inference service doubled while p50 is unchanged. How do you investigate?

If the SLO is breached, roll back first and investigate on a canary or in staging. Then: p50 unchanged with a worse p99 means the slowdown is intermittent, or tied to load or to a subset of requests, not a uniformly slower code path.

Narrow it down with data.

  • Which replicas, endpoints, tenants, request sizes? One bad node looks very different from a fleet-wide shift.
  • Diff the deploy: code, dependencies, model, config, base image, resource limits, replica count.
  • Break latency into stages with tracing: queue wait, preprocessing, model, post-processing, downstream calls. Find which stage owns the tail.

Usual suspects, by signature.

  • Tail tracks input length. A new model or a batching change (padding to the longest sequence in the batch).
  • Tail in queue wait. Fewer replicas, a lower concurrency limit, a changed batching window, or throughput per replica dropped slightly and pushed utilisation toward saturation.
  • Spikes at a round number (exactly 1 s, 5 s). A downstream timeout followed by a retry.
  • Unrelated requests slow at the same moment. Something blocks the event loop (a synchronous call in an async handler) or a thread pool is saturated.
  • Periodic spikes. Garbage collection, a background job, cache expiry, a metrics flush.
  • CPU throttling. The container’s CPU quota is lower than the threads it runs; check the cgroup nr_throttled counter.
  • Only new replicas. Cold start: lazy model load, first-call compilation, cold caches.
  • Shape-dependent recompilation or algorithm search on input shapes not seen during warm-up.

Tools. Per-stage latency histograms, a latency heat map over time, per-replica comparison, py-spy dump during a slow period, an event-loop-lag metric.

Verify. Reproduce with a load test at a constant arrival rate (open loop). A closed-loop generator that waits for each response slows down with the server and under-reports the tail (coordinated omission).

Follow-ups

  • Throughput per replica dropped 5%. How can that double p99?
  • How do you detect that the event loop is being blocked in production?

coreconceptMLE AI RE Explain at-most-once, at-least-once and exactly-once. How do you make a retried request or a redelivered message safe?

A sender that gets no reply cannot tell whether the request was lost or the reply was. It has two choices: do not retry (at-most-once, work may be lost) or retry (at-least-once, work may be duplicated). Exactly-once delivery is not achievable under failures. What systems provide is exactly-once effect: at-least-once delivery plus processing that is idempotent or transactional.

Idempotency. An operation whose effect is the same applied once or many times.

  • Naturally idempotent: set a value, delete by id, upsert keyed by event id, overwrite a partition.
  • Made idempotent: the client generates a unique key per logical operation; the server records the key and the result in the same transaction as the effect, and replays the stored result on a repeat.
  • Consumers: a dedup table keyed by message id, or committing the input offset atomically with the output. Kafka transactions make consume-process-produce atomic inside Kafka; an email, a payment or a launched GPU job outside it is still at-least-once.

Retry policy.

  • Retry only errors that can succeed later (timeouts, 503, 429), never validation errors.
  • Exponential backoff with jitter: sleep a random time in \([0, \min(\text{cap}, \text{base}\cdot 2^{n})]\). Without jitter, clients that failed together retry together.
  • Bound attempts and add a retry budget (for example, retries at most 10% of requests), so an outage is not amplified into a retry storm.
  • Retries multiply across layers: three layers with three attempts each can produce 27 calls. Retry at one layer and propagate deadlines.

ML examples: a replayed event stream double-counts clicks in training data; an agent tool sends the same email twice after a timeout; a re-run batch-inference job appends duplicate rows instead of overwriting its date partition.

seniortrade-offMLE AI RE What consistency guarantees can a replicated store offer, and which would you pick for an online feature store, a model registry and a rate-limit counter?

The models, strongest first.

  • Linearizable. The store behaves like a single copy: once a write completes, every later read sees it. Needs consensus (Raft, Paxos): a majority must acknowledge, so \(2f+1\) nodes tolerate \(f\) failures, writes cost a quorum round trip, and a minority partition cannot serve.
  • Causal and session guarantees. Read-your-writes, monotonic reads: weaker, but enough for most user-facing flows.
  • Eventual. Replicas converge once writes stop. Concurrent writes need a resolution rule: last-writer-wins (silently drops writes under clock skew), version vectors, or CRDTs.

Quorum replication with \(N\) replicas, \(W\) write acknowledgements and \(R\) read replicas makes a read overlap the latest write when \(R + W > N\) (for example \(N=3\), \(W=2\), \(R=2\)). That alone is not linearizability.

CAP says that during a partition you choose consistency or availability; PACELC adds that without a partition you still trade latency against consistency. Isolation levels (serializable, snapshot) are a separate axis about concurrent transactions.

Choices.

  • Online feature store. Eventual with bounded staleness. Features are already seconds to hours old, and availability and p99 matter more. Monitor replication lag as a feature-freshness metric.
  • Model registry and deployment config (“which version is production”). Linearizable or transactional: small data, few writes, and two servers disagreeing about the live model is a correctness bug. Use a relational database or etcd.
  • Rate-limit counter. Approximate: local counters synchronised periodically; slight over-admission is acceptable.
  • Usage and billing ledger. Transactional and idempotent.

The classic failure is assuming read-after-write on an asynchronous replica: the user updates a setting, the next request reads a lagging replica and sees the old value. Route those reads to the leader or carry a version token.

seniortrade-offMLE AI RE How do you partition data or traffic across nodes, and how do you handle rebalancing, hot keys and queries that must touch every shard?

Schemes.

  • Hash, hash(key) mod N. Even load, but changing \(N\) remaps almost every key.
  • Consistent hashing. Keys and nodes are hashed onto a ring; a key belongs to the next node clockwise. Adding or removing a node moves about \(K/N\) of \(K\) keys. Virtual nodes (many ring positions per machine) even out the load. Rendezvous hashing, or a fixed number of logical partitions assigned to nodes (Redis Cluster uses 16,384 slots), achieve the same.
  • Range. Supports ordered scans, but sequential keys such as timestamps all land on the last partition. Prefix the key with a hash bucket.

Rebalancing. Move whole partitions, not individual keys; throttle the copy; serve reads from both the old and new owner during the move.

Hot keys. A celebrity account, a NULL key, one very popular prompt. Hashing does not help, because one key is one partition. Options: cache in front, split the key with a suffix and aggregate on read, isolate it on dedicated capacity, or limit it.

Scatter-gather. A query that fans out to \(n\) shards waits for the slowest one. If each shard exceeds its p99 with probability 0.01, at least one does with probability \(1 - 0.99^{n}\): 63% for \(n = 100\). Mitigate with hedged requests, per-shard deadlines with partial results, and fewer, larger shards.

In ML systems.

  • A sharded vector index queries every shard for its top \(k\) and merges, so tail latency grows with the shard count.
  • Routing by conversation or user id with consistent hashing keeps a session on the same replica, so prefix caches stay warm.
  • In Kafka the partition key decides ordering (guaranteed only within a partition) and the unit of parallelism.
  • Sharded embedding tables: skewed id frequency makes some shards much hotter than others.

staffdesignMLE AI Requests arrive faster than your GPU fleet can serve them. Walk through queues, backpressure, rate limiting and load shedding, and say what you would build first.

A queue absorbs bursts; it does not fix sustained overload. With arrival rate \(\lambda\) and service rate \(\mu\), the M/M/1 mean time in system is \(1/(\mu - \lambda)\): it grows without bound as utilisation \(\rho = \lambda/\mu\) approaches 1, and for \(\lambda > \mu\) the queue grows forever. So queues must be bounded and the system must be able to say no.

Layers, in the order I would build them.

class TokenBucket:
    def __init__(self, rate: float, burst: float):
        self.rate, self.burst = rate, burst
        self.tokens, self.t = burst, time.monotonic()

    def allow(self, cost: float = 1.0) -> bool:
        now = time.monotonic()
        self.tokens = min(self.burst, self.tokens + (now - self.t) * self.rate)
        self.t = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False

seniortrade-offMLE AI Where would you put caches in an ML serving path, and what goes wrong with each?

What is cacheable.

  • Feature lookups per user or item, with a TTL of seconds to minutes.
  • Embeddings, keyed by content hash and model version.
  • Whole responses for deterministic requests, keyed by a hash of model version, normalised input and parameters.
  • Retrieval results and, for LLMs, the computed state of a shared prompt prefix.

Whether it pays depends on the request distribution: head-heavy traffic caches well, a long tail does not. Expected latency is \(h\,t_{\text{hit}} + (1-h)\,t_{\text{miss}}\), but the tail does not improve unless the hit rate \(h\) exceeds the percentile: with 90% hits, p99 is still a miss.

Patterns. Cache-aside (read cache, on miss read the source and populate) is the default; write-through keeps the cache current at the cost of write latency. Invalidate by TTL or, better, by versioned keys: put the model or feature version in the key so a deploy invalidates naturally.

Failure modes.

  • Stampede. A hot key expires and many requests recompute it at once. Use single-flight (one loader per key), jittered TTLs, or serve stale while refreshing.
  • Cold start. After a deploy or restart the cache is empty, latency jumps and the backends take full load. Warm it, or ramp traffic gradually. If the system cannot survive an empty cache, the cache is a hard dependency and its failure is an outage.
  • Staleness. Acceptable for a slowly changing embedding, not for a price or an account balance.
  • Wrong key. A personalised response stored under a shared key leaks data between users; a key without the experiment arm or model version contaminates A/B tests.
  • Nondeterminism. Caching a sampled generation changes product behaviour: the same question always gets the same answer.
  • Write races. Updating the database and the cache separately can leave them inconsistent; delete the cache entry after the write commits and rely on TTL as the backstop.

Monitor hit rate, latency by hit and miss, eviction rate and entry age.

seniorconceptMLE RE As an ML engineer, what should you be able to explain about C++ ownership (RAII, smart pointers, move semantics), and why are inference runtimes written in C++?

RAII. A resource’s lifetime is tied to an object’s scope: the constructor acquires, the destructor releases, and the destructor runs deterministically at scope exit, including when an exception unwinds the stack. It covers memory, file handles, mutexes (std::lock_guard) and GPU buffers. There is no garbage collector, so there are no collector pauses.

Ownership in the type.

  • std::unique_ptr<T>: single owner, no overhead, move-only.
  • std::shared_ptr<T>: shared ownership through an atomic reference count; copying it costs an atomic increment. std::weak_ptr breaks cycles.
  • Raw pointers and references mean “not the owner”.
  • Rule of zero: let members manage resources. If you write one of destructor, copy or move operations, you probably need all five.

Move semantics. std::move is a cast to an rvalue reference. The move constructor then takes over the source’s buffer in \(O(1)\) instead of deep-copying in \(O(n)\); the source stays valid but unspecified. Mark move constructors noexcept, otherwise std::vector copies elements when it reallocates. Returning by value is cheap through copy elision. Pass large read-only objects by const& or std::span.

Typical bugs. Dangling references, use-after-free, iterator invalidation after push_back, data races, undefined behaviour. Tools: AddressSanitizer, ThreadSanitizer, UBSan.

Why inference stacks use it.

  • Real multi-threading with no GIL.
  • Control over memory layout and allocation (arenas, pinned memory, zero-copy between stages).
  • Direct access to CUDA, TensorRT, SIMD intrinsics.
  • No interpreter overhead per operation, which matters for small models at high QPS.
  • Predictable tail latency, and it embeds in non-Python hosts (mobile, vehicles, trading systems).

PyTorch is a Python front end over a C++ core; ONNX Runtime, TensorRT, Triton and llama.cpp are C++.

seniorconceptMLE AI Walk through what happens on the network when a client calls a streaming inference endpoint over HTTPS. Where do latency and failures come from?

Connection setup. DNS lookup (cached for its TTL), TCP three-way handshake (one round trip), TLS 1.3 handshake (one more; two with TLS 1.2), then the request. A new connection therefore costs two or more round trips before the server sees the request, which is 200 ms or more across continents. Connection pooling and keep-alive remove that cost; a client that opens a connection per request pays it every time.

HTTP versions.

  • HTTP/1.1: one request at a time per connection.
  • HTTP/2: many streams multiplexed over one TCP connection; gRPC runs on it. A lost packet stalls every stream on that connection (TCP head-of-line blocking).
  • HTTP/3: QUIC over UDP, per-stream loss recovery.

Load balancing. L4 balances connections, L7 balances requests. Long-lived HTTP/2 and gRPC connections pin a client to one backend behind an L4 balancer: load is uneven, and newly added replicas receive nothing until connections recycle. Use an L7 proxy or client-side balancing.

Streaming specifics.

  • Proxies that buffer responses must be configured to pass chunks through.
  • Idle timeouts (often around 60 s by default) cut a stream that pauses, for example during a long tool call; send heartbeats.
  • TCP flow control is the backpressure: a slow reader fills its receive window and the server’s writes block.
  • The server learns of a disconnect only when a write fails or a keep-alive probe times out; cancel generation then.

Latency and failure sources.

  • Nagle’s algorithm interacting with delayed ACKs adds tens of milliseconds to small writes; set TCP_NODELAY.
  • Retransmission after loss: Linux’s minimum retransmission timeout is 200 ms, so a little loss creates a visible tail.
  • Missing timeouts. Connect, read and total deadlines are separate, and a missing read timeout hangs forever on a half-open connection.
  • Port or connection-table exhaustion under high connection churn.

Where it is. Spark (Scala), Flink, Kafka, Hadoop, Lucene/Elasticsearch and Cassandra are JVM systems, and many product backends are Java or Kotlin. ML engineers meet it in data pipelines and at the serving boundary.

Runtime behaviour.

  • Bytecode is JIT-compiled as it gets hot, so a fresh instance is slow for its first requests. Benchmark after warm-up and warm new instances before they take traffic.

def longest_k_distinct(s: str, k: int) -> int:
    count = defaultdict(int)
    best = left = 0
    for right, ch in enumerate(s):
        count[ch] += 1
        while len(count) > k:          # shrink until the window is valid again
            c = s[left]
            count[c] -= 1
            if count[c] == 0:

            left += 1
        best = max(best, right - left + 1)

    def feasible(cap: int) -> bool:
        parts, cur = 1, 0
        for x in nums:
            if cur + x > cap:
                parts += 1
                cur = x
            else:
                cur += x
        return parts <= m

    lo, hi = max(nums), sum(nums)      # the answer lies in [lo, hi]
    while lo < hi:
        mid = (lo + hi) // 2
        if feasible(mid):

        else:
            lo = mid + 1                # mid fails: discard it
    return lo

class DSU:
    def __init__(self, n: int):
        self.parent = list(range(n))
        self.size = [1] * n

    def find(self, x: int) -> int:
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]   # path halving
            x = self.parent[x]
        return x

    def union(self, a: int, b: int) -> bool:
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                                   # already connected
        if self.size[ra] < self.size[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra
        self.size[ra] += self.size[rb]
        return True

        key = math.log(u) / w                  # log of u ** (1 / w)

Proof for the uniform case: item \(n\) (1-based) enters with probability \(k/n\). At a later step \(t\) it is evicted with probability \(\frac{k}{t}\cdot\frac{1}{k} = \frac{1}{t}\), so it survives with \(\frac{t-1}{t}\). The product telescopes:

\[\frac{k}{n}\cdot\frac{n}{n+1}\cdots\frac{N-1}{N} = \frac{k}{N}.\]

Weighted: give each item the key \(u_i^{1/w_i}\) and keep the \(k\) largest keys. This is equivalent to drawing items one at a time with probability proportional to weight among those remaining. It does not make the inclusion probability proportional to \(w_i\) when \(k > 1\). Taking logs twice shows it is the Gumbel top-k trick: rank by \(\log w_i + G_i\).

Pitfalls: randint bounds (off by one breaks uniformity), random.random() can return 0, working in log space to avoid underflow for small weights. Keyed reservoirs merge across shards by keeping the top \(k\) keys overall, which is how you sample uniformly from a distributed log.

seniorconceptMLE AI RE You need the mean, variance, p99, distinct count and heavy hitters of a stream of billions of events in bounded memory. What do you use for each, and what are the error guarantees?

Pick structures that are mergeable, so partial results from shards or time windows combine without the raw data.

  • Mean and variance: Welford’s update, exact and numerically stable in \(O(1)\) memory: \[\mu_n = \mu_{n-1} + \frac{x_n - \mu_{n-1}}{n},\qquad M_n = M_{n-1} + (x_n - \mu_{n-1})(x_n - \mu_n),\qquad s^2 = \frac{M_n}{n-1}.\] Accumulating \(\sum x^2\) and subtracting loses precision by cancellation. For a recency-weighted mean use an EMA \(m_t = (1-\alpha)m_{t-1} + \alpha x_t\) with bias correction \(m_t / (1 - (1-\alpha)^t)\), as Adam does.
  • Median, exact: two heaps (max-heap for the lower half, min-heap for the upper), \(O(\log n)\) per insert but \(O(n)\) memory.
  • Quantiles, approximate: t-digest (most accurate at the tails, which is what p99 needs), KLL or Greenwald-Khanna (rank error at most \(\epsilon n\)), or fixed-bucket histograms (error bounded by the bucket width). Averaging per-host p99 values does not give the fleet p99; merge sketches or histograms.
  • Distinct count: HyperLogLog, relative standard error about \(1.04/\sqrt{m}\) for \(m\) registers; \(2^{14}\) registers give about 0.8% in roughly 12 KB.
  • Frequencies: count-min sketch with width \(\lceil e/\epsilon \rceil\) and depth \(\lceil \ln(1/\delta) \rceil\) overestimates a count by at most \(\epsilon N\) with probability \(1-\delta\). Misra-Gries or Space-Saving for the top items.
  • Membership: Bloom filter, no false negatives, false-positive rate \((1 - e^{-kn/m})^k\); about 10 bits per item gives 1%.

Typical ML uses: feature statistics for normalisation and drift monitoring, latency percentiles, deduplicating crawl or training data, vocabulary counts.

seniorderivationMLE AI RE Show how you derive a dynamic program from scratch, using edit distance. Then tell me how you recognise that a problem needs BFS or Dijkstra instead of a DP table.

A DP is value propagation over a graph of states whose dependency order is known in advance. The derivation is mechanical:

  1. Brute force as decisions. Align the last characters of \(a[1..i]\) and \(b[1..j]\): match or substitute, delete from \(a\), or insert into \(a\).
  2. State. What must the remaining problem know? Only the two prefix lengths. Say it in one sentence: \(d[i][j]\) is the minimum number of edits turning \(a[1..i]\) into \(b[1..j]\).
  3. Recurrence from the last decision. \[d[i][j] = \min\big(d[i-1][j] + 1,\; d[i][j-1] + 1,\; d[i-1][j-1] + [a_i \ne b_j]\big)\]
  4. Base cases. \(d[i][0] = i\), \(d[0][j] = j\).
  5. Order. Each state depends on smaller \(i\) or \(j\), so row by row is a valid topological order.
  6. Cost. \(O(mn)\) time; \(O(\min(m, n))\) memory with two rolling rows, unless the alignment itself must be recovered.

Common state families: one prefix index (house robber, LIS), two indices (LCS, edit distance), interval \([i, j]\) (matrix chain), index plus capacity (knapsack, pseudo-polynomial), bitmask for \(n \le 20\) (TSP in \(O(n^2 2^n)\)), tree DP, and (node, resource used) for constrained shortest paths.

A table works only when the state graph is acyclic. If states can be revisited (moves in four directions on a grid, cyclic graph), the order must be discovered: BFS for unit costs, 0-1 BFS for costs in \(\{0, 1\}\), Dijkstra for non-negative costs, Bellman-Ford with negative edges.

ML instances: word error rate is edit distance over words; Viterbi and the CTC forward pass are DPs over (time, state); beam search is an approximation, not a DP.

seniorconceptMLE AI RE What does Rust’s ownership model guarantee, what does it not guarantee, and where does Rust actually appear in ML systems?

Rules.

  • Every value has exactly one owner and is dropped when the owner goes out of scope (RAII, no garbage collector).
  • Assignment and argument passing move by default; using a moved value is a compile error.
  • Borrowing: at any time either any number of shared references &T or exactly one mutable reference &mut T, and no reference may outlive its referent (lifetimes).
  • Send and Sync mark which types may be moved to or shared between threads; shared mutable state is written as Arc<Mutex<T>>.
  • Errors are values: Result<T, E> with ?, and Option<T> in place of null.

Guaranteed in safe code, at compile time: no use-after-free, no double free, no iterator invalidation, no data races.

Not guaranteed: deadlocks, logic errors, leaks through Rc cycles, panics, and anything inside unsafe (which FFI to C or CUDA libraries requires).

Costs. Long compile times, a real learning curve, awkward graph-shaped data structures (use indices or arenas), and a much thinner GPU and numerical ecosystem than C++.

Where it appears. Hugging Face tokenizers and safetensors, Polars, pydantic-core, the uv and ruff tools, vector databases such as Qdrant and LanceDB, the request router of text-generation-inference, and the Candle and Burn frameworks. The usual shape is a Rust core with Python bindings through PyO3, which lets the library release the GIL and parallelise across cores.

Against C++: same performance class; Rust enforces by default what C++ leaves to discipline and sanitizers; C++ still owns GPU kernels and the existing runtimes. For an ML engineer the interview level is usually “explain ownership and read the code”, unless the role is an inference or infrastructure role that lists Rust as a requirement.
