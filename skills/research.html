The senior bar

What separates a senior answer from a mid-level one in this area.

  • States the hypothesis and the result that would falsify it before describing the experiment, and knows the seed-to-seed noise floor of the metric being moved.
  • Distrusts a good result first and can list the leakage, baseline and evaluation checks run before believing a gain.
  • Debugs by bisection against a known-good reference instead of guessing, and can name the silent bugs (schedule not applied, frozen parameters, eval preprocessing mismatch) from experience.
  • Treats iteration time as a design target, knows where the time goes in the experiment loop and has shortened it.
  • Presents past research with an exact account of their own contribution, the strongest objection to the result, and what they would do differently.
  • Decides when to stop, with kill criteria set in advance, and writes up negative results so that nobody repeats them.
  • Discusses safety and fairness with definitions, measurements and costs, and separates established results from open questions.

coreconceptMLE AI RE What sanity checks do you run before launching a long training job?

Checks that take minutes and catch most bugs that would otherwise cost a day:

  • Loss at initialisation. For a \(C\)-class softmax with uniform predictions the loss is \(\ln C\): about 2.30 for 10 classes, about 10.82 for a 50,257-token vocabulary. For an imbalanced binary task, initialise the output bias to \(\log\frac{p}{1-p}\) and expect the entropy of the base rate. A different value means a bug in the loss, labels or initialisation.
  • Overfit one batch. Train on a single small batch with regularisation off; the loss should approach zero and predictions should match labels. Failure means the model, loss or optimiser wiring is broken.
  • Look at the exact tensors entering the model. Decode token ids back to text, display augmented images, print the labels next to them. Check the shift between inputs and targets for language models, and padding and attention masks.
  • Input-independent baseline. Zero the inputs; the model should do worse than with real inputs. If not, it is not using them.
  • Dependency check. The gradient of example \(i\)’s loss with respect to example \(j\)’s input should be zero; for causal models, with respect to future positions too.
  • Counts. Trainable parameter count, dataset size, steps per epoch, learning rate at a few steps of the schedule.
  • Evaluation path. Evaluate a known checkpoint and get its known number. Run evaluation and checkpoint-saving at step 10 so that they do not crash at hour 6.
  • Short run. A small-scale run whose loss curve looks like past good runs.

Follow-ups

  • The model overfits one batch but the full run does not learn. What does that rule out, and what is left?
coreconceptMLE RE How do you make a PyTorch training run reproducible, what remains nondeterministic, and why do you still need several seeds?

What to control.

  • Seed every generator: Python random, NumPy, torch.manual_seed (CPU and CUDA). Give the DataLoader a seeded generator and a worker_init_fn, because each worker process has its own state.
  • Request deterministic kernels: torch.use_deterministic_algorithms(True), torch.backends.cudnn.benchmark = False, and CUBLAS_WORKSPACE_CONFIG=:4096:8 for some cuBLAS operations.
  • Save and restore RNG states in checkpoints, or a resumed run diverges from an uninterrupted one.
  • Record the code version, config, library versions and hardware type.

What remains. Floating-point addition is not associative, so anything that changes the order of operations changes the low bits: a different GPU model, library version, number of devices, or batch size. Some CUDA operations have no deterministic implementation and raise an error under the flag above. Deterministic kernels can be slower. Bit-exact reproduction is realistic on the same hardware and software stack, and not across them.

Why seeds are still needed. Determinism and seed variance answer different questions. Determinism is for debugging: I can replay a failure exactly. Seed variance is a property of the method to be measured: a fixed seed gives one sample from the distribution of outcomes, and comparing two methods on one seed each confounds the method with luck.

It helps to separate the seeds for initialisation, data order and evaluation sampling, so that the source of variance can be identified.

Follow-ups

  • A resumed run does not match the uninterrupted one. Where do you look?
  • Which contributes more variance in your experience, initialisation or data order, and how would you measure it?
seniorcodingMLE RE Show me the unit tests you would write for numerical model code, for example a custom attention layer or loss.

Four kinds of tests catch most silent errors: gradient checks, causality, batch independence, and equivalence to a slow reference.

import torch

def test_gradcheck():
    # double precision: float32 finite differences are too noisy
    x = torch.randn(3, 5, dtype=torch.double, requires_grad=True)
    assert torch.autograd.gradcheck(my_fn, (x,), eps=1e-6, atol=1e-4)

def test_causal(model, vocab=100, T=16, t=10):
    model.eval()
    x = torch.randint(vocab, (2, T))
    x2 = x.clone()
    x2[:, t] = (x2[:, t] + 1) % vocab          # change one token
    y, y2 = model(x), model(x2)                 # (B, T, V)
    assert torch.allclose(y[:, :t], y2[:, :t], atol=1e-5)   # past unchanged
    assert not torch.allclose(y[:, t], y2[:, t])            # present changed

def test_batch_independence(model, x):
    model.eval()
    assert torch.allclose(model(x)[0], model(x[:1])[0], atol=1e-5)

def test_matches_reference():
    torch.manual_seed(0)
    logits = torch.randn(4, 7)                  # non-square on purpose
    y = torch.randint(7, (4,))
    ref = -torch.log_softmax(logits, -1)[torch.arange(4), y].mean()
    assert torch.allclose(my_cross_entropy(logits, y), ref, atol=1e-6)

Pitfalls an interviewer checks:

  • Use random inputs with distinct sizes on every axis. Zeros, ones and square shapes hide transposed dimensions and wrong broadcasts.
  • Test padding: a padded batch must give the same output for each sequence as running it alone.
  • Test the vectorised implementation against a loop-based one written for clarity, not speed.
  • Set tolerances by dtype (about \(10^{-5}\) for float32, \(10^{-10}\) for float64), and test mixed precision separately.
  • Test train() and eval() modes when dropout or normalisation layers are present.
  • Keep the tests small enough to run on CPU in seconds, so that they run on every commit.

These tests check invariants, which hold whatever the weights are; they complement the overfit-one-batch check, which tests learning.

Follow-ups

  • Your gradcheck fails only for some inputs. What are the likely causes?
  • How would you test a KV-cache implementation of incremental decoding?
seniortrade-offMLE RE How do you manage configurations and hyperparameter sweeps so that results stay reproducible and comparisons stay fair?

Configuration. One structured, typed config per run is the single source of truth; code reads nothing from undeclared globals or environment variables. Every run stores the fully resolved config (after overrides and defaults), the git commit and any uncommitted diff, the dataset version, library versions, seeds and the launch command. Changing a default silently changes the meaning of old configs, so stored configs must be resolved, and defaults change only with a version note. Flags for dead experiments are deleted, or the config becomes unreadable.

Sweeps.

  • Random search over grid when only a few hyperparameters matter: a grid of \(9\) points in two dimensions tests \(3\) values of the important one, random search tests \(9\) (Bergstra and Bengio, 2012). Sample learning rates and regularisation log-uniformly.
  • Bayesian optimisation when runs are expensive and the space is small (under about ten dimensions).
  • Early-stopping schedulers (successive halving, Hyperband, ASHA) to spend compute on promising trials. The risk is a bias against configurations that start slowly, such as low learning rates or larger models; check with a few full-length runs.

Fairness. The baseline and the new method get the same search space size and trial count. Select on validation data only. Sweep with one seed, then rerun the top few configurations with several seeds, because the best of 50 noisy trials is biased upwards. Report sensitivity (how wide the good region is), not only the best point.

The trade-off is flexibility against discipline: a rigid schema slows the first prototype, and pays for itself once two people need to compare runs.

Follow-ups

  • The best trial of a 50-trial sweep beats baseline by 0.5. Why can you not report that number?
  • How do you choose the search range for the learning rate?
coreconceptMLE AI RE What does good experiment hygiene look like, and what makes a negative result worth trusting?

Hygiene.

  • Write the hypothesis and the expected outcome before launching. One change per run.
  • Commit before running; the run records the commit, config, data version and seed.
  • Rerun the baseline in the current code and data version. Comparing with a number from three months ago compares codebases.
  • Never select on the test set. Keep a held-out set that is touched rarely.
  • Keep every run, including failures, in the tracker with a note. Deleting the losers turns the record into a selection.
  • Keep a dated log: what was run, why, the result, the next step. Plots carry the run ids that produced them.
  • Name runs so that the difference from the baseline is readable.

A credible negative result needs more care than a positive one, because “it did not work” is also what a bug produces.

  • A positive control passed: the same pipeline detects an effect known to exist.
  • The implementation was verified by tests or against a reference.
  • The idea had a fair tuning budget, not one run with default settings.
  • The uncertainty is stated: “no effect larger than 0.3 points at 95% confidence over 5 seeds”, not “no effect”.
  • The scope is stated: model size, data, the regimes not tried.

A one-page write-up with these elements stops colleagues from repeating the work and says under what conditions the idea might deserve another look.

Follow-ups

  • How do you stop a team from re-running an idea that failed a year ago, without discouraging a justified retry?
seniordebuggingMLE RE A training run completes with no errors and a falling loss, but the final metric is two to three points below what you expected. How do you find the cause?

I find a known-good reference and bisect, splitting the problem into evaluation, data, optimisation and model.

  1. Reference. The last commit and config that produced the expected number. Rerun it now. If it also underperforms, the cause is outside the code diff: data version, environment, hardware. If it is fine, bisect commits and config differences.
  2. Evaluation or training? Evaluate a known-good checkpoint with the current evaluation code. Then compare training-loss curves with the reference at equal steps: a gap from the start points to data or optimisation; an equal training loss with worse evaluation points to evaluation or overfitting.
  3. Data. Inspect decoded batches after all transforms. Check label distribution, shuffling, duplicated or dropped shards, truncation length, and augmentation applied at evaluation.
  4. Optimisation. Log the learning rate per step (a scheduler that is never stepped is common), gradient norm before clipping (clipping at every step means the threshold is too low), effective batch size under accumulation and multi-GPU, and which parameters receive weight decay.
  5. Model. Count trainable parameters (accidental freezing), check train()/eval() mode, dropout at evaluation, mask and padding handling, initialisation, whether the loaded pretrained weights matched all keys (strict=False hides mismatches).
  6. Numerics. Mixed-precision overflow, loss scaling, an \(\epsilon\) that is too large for half precision.
  7. Evaluation details. EMA weights not used, preprocessing different from training, a changed metric implementation.

Per-layer gradient norms and update-to-weight ratios (around \(10^{-3}\) is a common rule of thumb) localise a layer that is not learning.

Follow-ups

  • There is no known-good reference because this is a new model. How do you proceed?
  • Training loss matches the reference exactly but evaluation is worse. List the three most likely causes.
seniordesignMLE RE Each experiment takes 20 hours, so the team gets one result per day. How do you make the loop faster?

Measure first, then cut along three lines: wasted time, proxy experiments, and parallelism.

Measure. Break a training step into data loading, host-to-device copy, forward and backward, optimiser, logging; and the job into start-up, training, evaluation and checkpointing. Check GPU utilisation: well below 100% usually means the input pipeline or synchronisation is the bottleneck.

Remove waste.

  • Input pipeline: more workers, pre-tokenised or pre-decoded shards, memory-mapped data, augmentation on GPU.
  • Compute: mixed precision, compiled models, larger batches with a scaled learning rate, no per-step .item() or host synchronisation.
  • Cache anything frozen: precompute the outputs of a frozen encoder once.
  • Evaluation: a small fixed subset often, the full set rarely, and off the training GPUs.
  • Start from a shared checkpoint when the question concerns late training.

Shorten the question. Use a proxy (smaller model, a data subset, fewer steps) and validate it: take past experiments with known full-scale outcomes and check that the proxy ranks them the same way. A proxy with poor rank correlation produces fast wrong answers.

Parallelise. Run the candidates as a parallel sweep instead of in sequence, and decide in advance what each outcome implies.

Fail fast. A two-minute smoke test that runs the training, evaluation and checkpoint code at tiny scale before submission; early-abort rules for runs that have clearly diverged.

Targets I use: seconds to minutes for debugging, under an hour for a directional signal, overnight only for confirmation runs.

Follow-ups

  • How do you validate that a small-scale proxy predicts the full-scale outcome?
  • GPU utilisation is 45%. Walk me through the next ten minutes.
seniordebuggingMLE AI RE A new model scores 98% where the previous best was 85%, with a small change. What do you check before telling anyone?

A jump of that size from a small change is more likely a leak or an evaluation bug than a discovery, so I try to break the result.

Leakage.

  • Train-test overlap: exact and near duplicates; the same user, patient, document or conversation on both sides (split by group); future data in training for a temporal task.
  • Target leakage: a feature computed from the label or after the outcome. If one feature carries almost all the importance, examine it.
  • Preprocessing fitted on all data: normalisation statistics, feature selection, vocabulary, deduplication keyed on labels.
  • Selection on the test set through early stopping or repeated hyperparameter tuning.
  • For LLMs: the benchmark in the pretraining data, or the answer present in the prompt or the retrieved context.

Evaluation bugs. The metric computed on the training split; failed or filtered examples dropped from the denominator; teacher forcing at evaluation; a broken baseline run; a changed metric definition.

Tests that try to break it.

  • Shuffle training labels: the score should fall to chance.
  • Remove or blank the input: an input-free model should be at the majority-class rate.
  • Evaluate on fresh data collected after the training cut-off.
  • Read fifty predictions with their inputs.
  • Recompute the metric with an independent implementation.
  • Look at the gain per slice: a uniform jump on every slice, including the hardest, is suspicious.

Only after these pass do I report it, with the checks listed. Scrutiny should be proportional to surprise.

Follow-ups

  • How do you detect near-duplicate leakage in a dataset of 100 million text examples?
  • The result survives all your checks. What do you do next?
seniordebuggingMLE RE Your change beats the baseline by 0.5 points with one seed and loses with another. How do you establish whether the improvement is real?

I measure the variance, test the difference properly, and then reduce the variance if needed.

Measure. Run at least five seeds per arm, better ten, and report mean, standard deviation and \(n\). Example: with \(\sigma = 0.4\) in both arms and \(n=5\), the standard error of the difference is \(0.4\sqrt{2/5} \approx 0.25\), so a 0.5 gain gives \(t \approx 2.0\) with 8 degrees of freedom, short of the 5% critical value of 2.31. With \(n=10\) the standard error is 0.18 and \(t \approx 2.8\), which is significant.

Pair. If both arms can share initialisation and data order, analyse paired differences; the shared noise cancels.

Locate the variance. Fix initialisation and vary data order, then the reverse, then repeat evaluation alone. If evaluation noise dominates (accuracy on \(n\) examples has standard error \(\sqrt{p(1-p)/n}\), about 0.95 points for \(p=0.9\), \(n=1000\)), a larger evaluation set is cheaper than more training runs.

Look at the distribution. A bimodal outcome, where some seeds fail outright, means the problem is instability (learning rate, warmup, initialisation), and fixing that matters more than the mean. A method that lowers variance without moving the mean can still be worth adopting.

Do not report the best seed, pick the seed on the test set, or stop adding seeds when the result turns significant.

If the effect is smaller than the resolution I can afford, I say so: “difference of 0.5, 95% interval from -0.1 to 1.1”.

Follow-ups

  • Why is stopping when the test first reaches significance a problem?
  • How would you compare two methods when each run costs a week of compute?

corebehaviouralMLE RE Tell me about a piece of research you are proud of. What exactly was your contribution?

What is tested. Depth of understanding, an honest account of your own role, and whether you can judge your own work. Interviewers at research labs are usually able to check the details.

Structure.

  1. The question and why it mattered, for a listener outside the subfield.
  2. What was known and why the obvious approach failed.
  3. The approach, with the single idea that made it work.
  4. The key result as a number, with the baseline and the uncertainty.
  5. Your contribution, stated exactly: “I proposed the loss, implemented training and ran all experiments; my co-author built the data pipeline.” Middle authorship is fine if the description is precise.
  6. Limitations, and what you would do differently now.

What interviewers probe. Why this approach and not the nearest alternative; what you tried that failed; how you know the gain is real (seeds, baselines, ablations); any technical detail on any slide; what happened afterwards (citations, adoption, a follow-up that refuted it); what you would do with six more months.

Mistakes. Using “we” throughout so that your role is unclear; presenting only successes; being unable to reproduce a derivation from your own paper; defending a weak result instead of acknowledging it; choosing your most prestigious paper instead of the one you know best.

For confidential industry work, describe the method class and relative gains, and say plainly what you cannot share.

Follow-ups

  • What is the strongest objection a reviewer raised, and were they right?
  • If you started this project today, what would you change?
seniorbehaviouralMLE AI RE You do not have first-author papers at the top conferences. How do you show a research or open-source track record?

What is tested. Postings that ask for publications usually accept equivalent evidence: that you can take an open-ended technical question to a result that others can inspect and use. The interviewer wants artifacts and the decisions behind them.

Evidence that counts.

  • Open-source work with substance: a merged feature or fix in a widely used library where you can explain the design discussion, the review feedback and the trade-off chosen; or a project you maintain, with users, releases and issue triage.
  • Reproductions and technical write-ups with real experiments, code and negative findings.
  • Internal research with a measured outcome: the hypothesis, the experiment, the effect size, the launch decision. Give relative numbers if absolute ones are confidential.
  • Workshop papers, technical reports, benchmark or dataset contributions, serious reviewing.

How to present it. One or two items in depth, not a list. For open source: the problem, the API or design decision, how you handled backwards compatibility and review, what maintenance cost it created. For internal work: the same structure as a paper talk.

Mistakes. Counting commits or stars; listing a paper you cannot discuss in detail; claiming a team result as your own; apologising for the lack of papers instead of showing the equivalent skill.

Be direct about the gap if asked: say what you have not done (for example, led a paper through peer review) and what you have done that exercises the same skills.

Follow-ups

  • Tell me about a design disagreement in a code review on that project and how it was resolved.

corederivationMLE AI RE Define the main group fairness criteria for a binary classifier and show why they cannot all hold at once.

Let \(A\) be the group, \(Y\) the outcome, \(\hat Y\) the decision and \(S\) the score.

  • Demographic parity: \(P(\hat Y=1\mid A=a)\) equal across groups.
  • Equalised odds: true-positive and false-positive rates equal across groups (\(\hat Y \perp A \mid Y\)). Equal opportunity requires only equal true-positive rates.
  • Predictive parity: equal precision, \(P(Y=1\mid \hat Y=1, A=a)\).
  • Calibration within groups: \(P(Y=1\mid S=s, A=a)=s\) for every group.

Incompatibility. For a group with base rate \(p\), counting false positives two ways gives

\[\mathrm{FPR} = \frac{p}{1-p}\cdot\frac{1-\mathrm{PPV}}{\mathrm{PPV}}\cdot(1-\mathrm{FNR}).\]

Derivation: per unit population, true positives are \(p(1-\mathrm{FNR})\) and false positives are \((1-p)\,\mathrm{FPR}\); also false positives equal true positives times \((1-\mathrm{PPV})/\mathrm{PPV}\). Equate and solve.

If two groups have different \(p\) and the same PPV, they cannot have both the same FPR and the same FNR unless prediction is perfect (Chouldechova, 2017). Kleinberg, Mullainathan and Raghavan (2016) prove the analogous result for calibrated scores. Demographic parity conflicts with calibration whenever base rates differ, since a calibrated score has group mean \(p\).

The consequence is that the choice of criterion is a decision about which errors matter for whom, and must be made per application. The COMPAS dispute was this theorem in practice: the tool satisfied predictive parity while false-positive rates differed between groups.

Follow-ups

  • Which criterion would you pick for a loan-approval model, and what does it cost?
  • Why can a calibrated score still produce unequal false-positive rates?
seniordesignMLE AI RE How would you measure bias in a generative system, for example an LLM used to draft candidate summaries for recruiters?

Start from the harm in this product, then build measurements for it; generic stereotype benchmarks are a supplement.

Harms here. Allocational: summaries that are systematically less favourable or less accurate for some groups, which changes who gets interviewed. Representational: stereotyped language.

Counterfactual paired evaluation (the core). Take real or realistic inputs and vary only the demographic signal (name, pronouns, a school or affiliation that signals group), keeping qualifications fixed. Generate summaries and compare, within pairs:

  • a favourability or recommendation score from a fixed rubric (human-rated on a sample, then a validated automated judge);
  • factual fidelity to the source (omissions and additions);
  • length, hedging, and the adjectives used.

Report the mean paired difference with a confidence interval per attribute. Use many templates and inputs, and several samples per prompt, because generation is stochastic and results are sensitive to phrasing.

Quality of service. Does accuracy fall for non-standard English, other languages, or career paths that are rarer in training data?

Downstream. If recruiters act on the summaries, measure selection rates by group in the product, since small textual differences can be amplified or ignored.

Benchmarks. Sets such as BBQ, StereoSet and CrowS-Pairs give a broad signal, but published critiques have found validity problems in some of them, and they do not test this task.

Pitfalls. The judge model may itself be biased, so validate it against human ratings by group; names are noisy proxies; intersectional slices get small; “no difference” needs a stated detectable effect size.

The measurement becomes a regression gate that runs on every model or prompt change.

Follow-ups

  • How many pairs do you need to detect a difference of 0.1 on a 5-point rubric?
  • For an image generator given “a doctor”, what is the right reference distribution?
seniortrade-offMLE AI You have measured a disparity between groups. What are the mitigation options and what does each cost?

First diagnose the source, because the cheapest fix depends on it: less or noisier data for one group, a label that encodes past decisions, a proxy feature, or a threshold that suits one group’s score distribution.

Options.

  • Data (pre-processing). Collect more or better-labelled data for the worse-off group; reweight or resample; fix the label definition. This is often the only option that improves fairness and accuracy together. Cost: time and money, and collection may need the sensitive attribute.
  • Training (in-processing). A constraint or penalty on the disparity, adversarial removal of group information, or group-robust objectives that optimise the worst group’s loss. Cost: usually some average accuracy, extra hyperparameters, less stable training, and guarantees that hold on training data more than at test time.
  • Decision (post-processing). Group-specific thresholds, or recalibration per group. Simple and auditable. Cost: needs the attribute at decision time, which is legally restricted in some domains and jurisdictions, so involve counsel.
  • Generative systems. Instructions, counterfactual data augmentation in fine-tuning, output filters. Over-correction produces its own errors, such as inaccurate outputs where the demographic fact matters.

Costs common to all.

  • Criteria conflict, so fixing one disparity can widen another.
  • Parity can be reached by making the better-off group worse (“levelling down”), which helps nobody.
  • Parity on coarse groups can hide disparity in subgroups.
  • Measurement needs sensitive attributes, which is in tension with data minimisation.
  • The fix can decay under distribution shift, so it needs monitoring.

I present the trade-off curve (disparity against utility) to the decision owner instead of choosing a point alone.

coreconceptMLE AI RE What makes an experiment informative?

An experiment is informative when its plausible outcomes would lead to different beliefs or decisions. The test: before running it, write down what each hypothesis predicts. If every hypothesis predicts the same result, or if no result would change what I do next, the experiment is not worth the compute.

Properties of an informative experiment:

  • Discriminating. It is aimed at the point where competing explanations disagree, not at where they agree.
  • Controlled. One thing changes. Otherwise a positive result cannot be attributed.
  • Above the noise floor. I know the run-to-run standard deviation of the metric and the effect I am looking for is larger, or I have enough seeds and evaluation examples to resolve it.
  • Has controls. A positive control (a known effect the pipeline must detect) shows that a null result means something; a negative control (a change that must do nothing, such as shuffled labels) shows that a positive result is not an artifact.
  • Cheap relative to what it settles. Prefer the small experiment that removes most of the uncertainty over the large one that removes all of it.

A useful ordering is by expected information per GPU-hour. Reading fifty failure cases or running a ceiling test often beats a week of training.

Writing the prediction first also guards against hindsight: if I would have explained either outcome, I learned nothing.

coretrade-offMLE AI RE Why insist on a simple baseline first, and what counts as a strong one?

A baseline gives the number that a new method must beat, and building it tests the whole pipeline (data, evaluation, logging) with a model simple enough that bugs are visible. Without it, a gain cannot be sized and a failure cannot be localised.

What counts as strong:

  • The simplest method that could work for the task: majority class, a linear model or gradient-boosted trees on tabular data, BM25 for retrieval, last-value or seasonal-naive for forecasting, a prompted off-the-shelf model for an LLM task.
  • The current method retuned with the same budget as the new one, on the same data, at the same compute.
  • “The same model, larger or trained longer”, which is the baseline many new methods fail to beat.

There is a published pattern of well-tuned baselines closing claimed gaps: Melis et al. (2018) for LSTM language models, Lucic et al. (2018) for GAN variants, Henderson et al. (2018) for deep RL, Musgrave et al. (2020) for metric learning, and Ferrari Dacrema et al. (2019) for neural recommenders.

The trade-off is time. Tuning a baseline can take as long as building the method, and it feels unproductive. I cap it: same search space and number of trials as the method gets. I skip it only when a trusted, recent number exists for exactly my data and evaluation code.

A side benefit: if the baseline is within noise of the goal, the project is finished early.

seniorconceptMLE AI RE State the bitter lesson and tell me how it should and should not influence a research decision.

Sutton’s 2019 essay argues, from the history of chess, Go, speech recognition and computer vision, that general methods which scale with computation (search and learning) have in the long run outperformed methods built on human knowledge of the domain, and that researchers repeatedly underestimate this because knowledge-based methods give quicker short-term gains.

Stated carefully, it is an empirical claim about long-run trends under growing compute, not a theorem.

How it should influence decisions.

  • Prefer the method whose advantage grows with data and compute. Test at two scales: if a hand-designed component gives +2 points on a small model and +0.3 on a model ten times larger, expect it to vanish.
  • Put human effort where it compounds with scale: data, objectives, evaluation, environments and tooling.

What it does not say.

  • It does not say structure is useless at a fixed budget. With limited data, latency limits or a deadline, inductive bias and domain features often win today. Product work lives at a fixed budget.
  • It does not say architecture is irrelevant: convolution and attention are human designs that made scaling possible.
  • It does not say compute is free; serving cost and energy are real constraints.
  • Domain knowledge does not disappear; it moves into the data, the reward and the evaluation.

A good answer names the time horizon and the budget of the decision at hand, then applies the lesson accordingly.

seniordesignMLE RE A colleague proposes a change to the training recipe (say a new learning-rate schedule) and reports a 0.4-point gain from one run. Design the experiment that tells you whether it really helps.

Claim and metric. Fix the primary metric, dataset and evaluation protocol before running anything. Decide the smallest effect worth adopting, say \(\delta = 0.3\) points.

Noise floor. Run the baseline with \(k\) seeds to estimate the standard deviation \(\sigma\) of the final metric. With per-arm sample size \(n\), detecting \(\delta\) at 5% two-sided significance and 80% power needs approximately

\[n \approx \frac{2\,(z_{0.975}+z_{0.8})^2\,\sigma^2}{\delta^2} = \frac{15.7\,\sigma^2}{\delta^2}.\]

If \(\sigma = 0.3 = \delta\), that is about 16 seeds per arm; if \(\sigma = 0.1\), two or three. If the count is unaffordable, reduce \(\sigma\): larger evaluation set, paired seeds (same initialisation and data order in both arms, analysed as paired differences), or averaging the last few checkpoints.

Fair comparison.

  • Retune the baseline’s schedule hyperparameters (peak rate, warmup) with the same search budget as the new schedule. A new schedule often just fixes a mistuned learning rate.
  • Same steps, batch size, data and compute. Compare at equal compute and at convergence.
  • Compare whole training curves, not only the endpoint; a schedule can be faster early and equal late.

Generality. Two model sizes and two datasets or tasks. An interaction with scale changes the decision.

Hygiene. Use the validation set for all selection; evaluate the test set once. Report every run, the mean difference with a confidence interval, and the sensitivity of each arm to its hyperparameters.

Decision rule. Adopt if the interval excludes zero and the lower bound is useful, the gain holds at the larger scale, and the method does not add fragile hyperparameters.

staffdesignMLE AI RE A deployed model fails on a class of inputs and nobody knows why. You have two weeks and one teammate. Plan the investigation.

Days 8-12: intervene. Data fix, pipeline fix or training change, evaluated on the frozen failure set, a held-out failure sample collected later, and the full regression suite.

Days 13-14: write up. Cause, evidence, fix, residual failure rate, monitoring added, what remains unknown.

staffdebuggingMLE RE Your method beats the baseline by two points. The ablation that removes the component you claim is responsible loses only 0.2. What do you do?

The evidence says the claimed mechanism is not what produces the gain, so either the ablation is wrong or the claim is. I check in this order.

  1. Noise. Is 0.2 versus 2.0 outside seed variance for both variants? Run enough seeds to say so.
  2. Is the ablation real? Verify that the component is disabled: log its outputs, assert on the code path, check the parameter count. A flag that is ignored is a common cause.
  3. Is the ablated model handicapped or helped by tuning? Hyperparameters were tuned for the full model. Retune the ablated variant; the fair comparison is best against best.
  4. Confounds bundled with the method. List every difference between the baseline and the full method: extra parameters, longer training, a different augmentation or data filter, a new normalisation, a changed evaluation path. Add each one to the baseline separately.
  5. Interactions. Leave-one-out ablations miss redundancy: two components may each be sufficient. Run a factorial design (at least 2x2) on the main components.
  6. Mechanism check. Measure the intermediate quantity the component is supposed to change. If it does not change, the story is wrong even if the number is right.

Then I update the claim to what the evidence supports. If the two points come from the training recipe, the finding is “the recipe matters”, and the baseline should receive it. The literature has cases of this kind, where architecture gains shrank once older models received modern training recipes.

What I would not do is leave the ablation out of the write-up.

coreconceptMLE RE What is the division of labour between a research scientist and a research engineer, and what does a good research engineer contribute beyond implementation?

  • A path to product. Knowing early what will block deployment.

Failure modes: the engineer as ticket-taker who implements without understanding the question; research code thrown over a wall; an infrastructure project that nobody’s experiments need.

  3. Human uplift studies: randomised groups with and without model access attempt a proxy task; the outcome is the difference in success or quality. Expensive, low sample size, closest to the threat model.
  4. Expert red-teaming for what the suites miss.

Elicitation. The evaluation must measure what a motivated user could extract, so use strong scaffolding and tools, several attempts, generous token budgets, and a variant without refusals. Under-elicitation produces false reassurance; this is the main validity risk. Test for sandbagging by checking consistency across framings.

Thresholds. Set them before running, with a margin: evaluations happen at intervals, capability rises between them, and elicitation improves after release.

Validity problems. Few tasks give wide confidence intervals; benchmarks saturate or leak; proxies must avoid being hazardous themselves; graders need domain experts.

If the threshold is crossed. Safeguards proportionate to the risk before deployment: misuse classifiers and monitoring for that domain, restricted access, stronger security for the weights, tested by red-teaming; or delay. The decision and evidence are reviewed by people independent of the team shipping the model.

The honest caveat: threshold placement is a judgment under uncertainty, and the science of these evaluations is young.

Follow-ups

  • How would you detect that a model is underperforming on purpose during an evaluation?
  • With 30 tasks and a 40% success rate, how wide is the confidence interval, and what does that mean for a threshold at 50%?
corebehaviouralMLE AI RE Why do you want to work on AI safety?

What is tested. Sincerity, knowledge of what the work consists of, and the ability to reason about uncertain claims. Interviewers at safety-focused labs hear rehearsed answers constantly and probe past them.

Structure of an honest answer.

  1. Your own reason, concretely. Examples of the kind of reason that holds up: failure modes you saw in deployed systems; a view that as models take more autonomous actions, reliability and misuse problems carry higher stakes; wanting to work where measurements gate deployment decisions.
  2. What you are unsure about. Say which arguments you find persuasive, which you do not, and what evidence would move you. Calibrated uncertainty reads better than conviction.
  3. What you want to do. Tie it to your skills: building evaluations, training classifiers, scaling interpretability experiments, securing agent execution.
  4. Evidence of engagement: a specific paper, system card or published safety framework from the lab you are interviewing with, and your opinion of it, including a criticism.

Mistakes. Slogans with no technical content; confident predictions about timelines or outcomes presented as fact; cynicism (“safety is marketing”); feigned passion; not having read the lab’s own published framework; treating safety and capability work as cleanly separable when much safety research needs capable models and can advance capability.

If your motivation is partly that the problems are technically interesting and the team is strong, say so. A plain mixed motive is more credible than a pure one.

Follow-ups

  • Which argument for concern about advanced AI do you find weakest, and why?
  • How would you feel about working on capability evaluations that might show the model is safe to release?
