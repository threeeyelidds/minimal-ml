The senior bar

What separates a senior answer from a mid-level one in this area.

  • Picks the least autonomous design that solves the task (single call, workflow, agent) and justifies it with error compounding, cost per task and cost of a wrong action.
  • Treats the model as an untrusted proposer, so permissions, argument validation, budgets, idempotency and approvals are enforced in code outside the model and never only in the prompt.
  • Reasons about context as a budgeted, cache-sensitive compiled state and can say what goes in, in what order, what is compacted and what is fetched on demand.
  • Separates retrieval failures from generation failures in RAG, measures each stage, and knows hybrid retrieval, reranking and permission filtering concretely.
  • Changes prompts, tools and models as versioned changes gated by a regression eval, and debugs incidents from traces rather than from guesses.
  • Quantifies cost and latency per completed task (input and output tokens, cache hit rate, time to first token, steps per task) and knows which lever moves which number.
  • Can scope work with a customer down to one measurable workflow, define acceptance criteria and carry it from demo to production.

coreconceptMLE AI RE What is an agent, concretely? Walk me through the loop and tell me which parts belong to the model and which to your code.

An agent is a model run in a loop where the model, not the code, picks the next action from what it has observed so far. It has four parts:

  • Model: proposes either a final answer or one or more tool calls.
  • Tools: typed functions the harness can execute (search, read, write, run code).
  • State: the message history plus anything kept outside the window (plan, files, event log).
  • Stop condition: the model answers without a tool call and the completion check passes, or a budget (steps, tokens, wall-clock, money) runs out, or the run needs a human, or a fatal error occurs.

One iteration: compile context from state, call the model, and if it requested tools then validate the arguments, check permissions, execute, append the bounded result as an observation and repeat.

The split that matters: the model owns judgment under ambiguity (which hypothesis to test, what is missing, how to read an unfamiliar error). Code owns invariants (step limits, schema validation, timeouts, permission checks, approval for destructive actions). A model proposal is not a side effect until the harness has parsed, authorised and executed it. If the control flow is fixed in code and the model only fills in steps, it is a workflow, not an agent.

coretrade-offMLE AI RE When does a fixed workflow beat an agent, and when is an agent worth it?

Use the least autonomy that solves the task. A single call for classification, extraction or Q&A; a workflow (code-defined steps, model fills each one) when the steps are known in advance; an agent only when the path depends on what is discovered along the way.

Why not default to an agent:

  • Compounding error. If each step succeeds independently with probability \(p\), an \(n\)-step run succeeds with about \(p^n\): \(0.95^{20} \approx 0.36\), \(0.99^{20} \approx 0.82\). This is a pessimistic bound only when the environment gives feedback the agent can use to recover (tests, error messages); silent errors compound fully.
  • Cost and latency. Every step re-sends the growing history, so uncached input tokens grow roughly quadratically in the number of steps.
  • Predictability. A workflow has enumerable paths that can be tested and audited.

An agent earns its cost when four things hold: the task is open-ended and hard to specify as steps; the outcome is valuable enough to pay for many calls; the model is actually good at the task; and errors are cheap to detect and undo (tests, review, rollback).

The common production shape is a hybrid: code fixes the outer stages and the invariants, and the model makes local decisions or runs a bounded loop inside one stage.

seniortrade-offAI RE Single agent or multiple agents? When do sub-agents help and what do they cost?

Start with one agent. Add sub-agents for a specific reason, not to mirror an org chart.

What sub-agents buy:

  • Context isolation. A sub-agent can read 100k tokens of search results or files in its own window and return a 1-2k token finding, keeping the lead’s context clean.
  • Parallelism. Independent sub-tasks run concurrently and cut wall-clock time.
  • Specialisation. Different tool sets, prompts or cheaper models per role.
  • Independent checking. A reviewer that has not seen the author’s reasoning is less anchored on it.

What they cost:

  • Tokens. Each sub-agent pays for its own context; total usage is typically several times a single agent’s.
  • Lossy hand-offs. The sub-agent knows only the brief, and the lead sees only the summary. Errors come back in the same confident tone as findings.
  • Coordination. Parallel agents that make interdependent decisions produce conflicts (two agents editing the same file, incompatible assumptions).

Good fit: breadth-first, read-heavy, separable work (research across sources, codebase search, per-document extraction). Poor fit: tightly coupled writing where every decision depends on shared context.

Rules that make it work: give each sub-agent an explicit brief (goal, what is already ruled out, output format, tool and scope limits); have it return compact, checkable results or pointers to artefacts; keep writes single-threaded; cap depth and fan-out.

Follow-ups

  • How would you measure whether a multi-agent version is worth its token cost?
  • What goes wrong if the lead forwards its own hypothesis in the brief?

seniordebuggingAI RE Your agent sometimes runs until it hits the step limit without finishing. How do you investigate and what do you change?

Read the traces of the runs that ended on the budget and classify them before changing anything. The usual causes:

  1. Repeated identical call. The tool returns an error the model cannot act on (“failed”), or the result never reaches the model (tool result not paired with its call id, or truncated to nothing), so it retries the same thing.
  2. Oscillation. Two fixes that undo each other, common when a verifier reports failure without saying what failed.
  3. No reachable stop. The definition of done is missing or the completion check can never pass (flaky test, impossible requirement).
  4. Lost state. Compaction dropped the fact that an approach was tried and failed.
  5. Unbounded exploration. Pagination or search with no convergence criterion.

Changes, in order:

  • Make errors actionable: what failed, why, and what input would be valid.
  • Detect loops in code: hash (tool, normalised arguments); after k repeats inject a notice, force a replan, or stop.
  • Hard budgets on steps, tokens and wall-clock, with a graceful exit that reports partial progress instead of an exception.
  • Give the model an explicit way out: “cannot complete, here is why” or ask the user.
  • Keep failed attempts and unresolved errors verbatim through compaction.

Then monitor the termination-reason histogram and the steps-per-task distribution (p50, p95), and add the looping cases to the regression set.

Follow-ups

  • How do you tell a legitimate long task from a loop?
  • The loop detector fires on a polling tool. What do you do?
seniordesignAI Design a customer-support agent for an e-commerce company that can answer questions and perform actions such as refunds.

Clarify first. Channels (chat, email, voice), volume, top intents, which actions are in scope, policy sources, the target (resolution rate at equal or better CSAT) and the cost of a wrong action.

Architecture.

  1. Intake: authenticate the customer, attach account context, run input checks.
  2. Routing: a small model classifies intent and risk; out-of-scope or sensitive intents go straight to a human.
  3. Knowledge: RAG over help-centre and policy documents, with document versions and effective dates, so policy answers are grounded and cited.
  4. Agent loop with tools: read tools (order status, shipment, account) run freely; write tools (refund, cancel, address change) are gated.
  5. Escalation: hand off with a structured summary (issue, steps taken, customer data gathered) so the human does not start over.

Controls outside the model. Tools take the authenticated customer id from the session, never from model arguments, and the backend re-checks ownership. Refunds carry an idempotency key; amounts above a limit, or repeated refunds, require human approval. Policy limits live in code. Customer messages and ticket text are untrusted input. PII is redacted in logs.

Evaluation. Offline: a golden set of conversations per intent, simulated multi-turn users, graders for policy adherence, correct tool use and groundedness. Online: resolution rate, reopen rate within 7 days, CSAT, escalation rate and its precision, cost per resolved conversation.

Rollout. Shadow mode, then draft-for-human, then autonomous on low-risk intents, then expand intent by intent.

Failure modes to name. Inventing policy, premature “resolved” to hit the metric, social-engineering for refunds, loops with frustrated users (cap turns and escalate).

  • How do you stop the agent from promising something the policy does not allow?
  • Which metric would the team game first, and what counter-metric do you add?
  • What changes for the voice channel?
corecodingMLE AI RE Write a minimal agent loop with tool calling against a generic chat-completions-style client. Then tell me what is missing for production.

Assume client.chat(messages, tools) returns {"content": str | None, "tool_calls": [{"id", "name", "arguments": <JSON string>}], "finish_reason": str}.

import json
import jsonschema

def run_agent(client, system, user_msg, tools, max_steps=20):
    """tools: {name: {"description": str, "parameters": <JSON Schema>, "fn": callable}}"""
    specs = [{"name": n, "description": t["description"], "parameters": t["parameters"]}
             for n, t in sorted(tools.items())]            # stable order keeps the prefix cacheable
    messages = [{"role": "system", "content": system},
                {"role": "user", "content": user_msg}]
    for _ in range(max_steps):
        reply = client.chat(messages=messages, tools=specs)
        messages.append({"role": "assistant", "content": reply["content"],
                         "tool_calls": reply["tool_calls"]})
        if reply["finish_reason"] == "length":
            raise RuntimeError("output truncated; tool arguments may be incomplete")
        if not reply["tool_calls"]:
            return reply["content"]                         # stop: answer without a tool call
        for call in reply["tool_calls"]:                    # one result per call, same id
            messages.append({"role": "tool", "tool_call_id": call["id"],
                             "content": execute(tools, call)})
    raise RuntimeError("step budget exhausted")

def execute(tools, call, max_chars=8000):
    try:
        tool = tools[call["name"]]                          # KeyError: hallucinated tool
        args = json.loads(call["arguments"])
        jsonschema.validate(args, tool["parameters"])
        out = tool["fn"](**args)
        text = out if isinstance(out, str) else json.dumps(out, default=str)
    except Exception as e:                                  # errors are observations
        text = f"ERROR {type(e).__name__}: {e}"
    return text[:max_chars]

Pitfalls an interviewer checks:

  • The assistant message with its tool calls must be appended before the results, and every call needs exactly one result with the matching id, or the next request is rejected.
  • Tool errors go back to the model as results; only harness faults raise.
  • A hard step limit and bounded tool output.

Missing for production: permission and approval checks before side-effecting tools, per-tool timeouts, retry with backoff on API errors, token and cost budgets, context compaction, concurrency for parallel-safe calls, an event log for resume, tracing, and a completion verifier.

Follow-ups

  • Where would you add human approval, and what is persisted while waiting?
  • How would you run the tool calls in parallel safely?

coreconceptMLE AI RE What is an agent harness, and what are its components?

The harness is everything around the model that turns a next-token predictor into a closed-loop system: it decides what the model sees, executes what the model proposes, and enforces what the model must not decide. The same model can score very differently under different harnesses, which is why postings ask for it by name.

Components:

  • Context compiler: assembles rules, task, tool definitions, working state, selected evidence and recent history for each call; handles ordering, truncation and compaction.
  • Tool registry and executor: schemas, argument validation, timeouts, output normalisation, side-effect class, retry semantics.
  • State and memory: append-only event log, working state (plan, budgets), artefacts on disk, long-term memory.
  • Controller: the loop itself, with termination conditions, budgets, retries, escalation, sub-agent and background-job lifecycles, resume after interruption.
  • Verifiers: tests, schema checks, citation checks; they turn “I think I am done” into evidence.
  • Permission layer: least privilege, sandboxing, approval for consequential actions; outside the model’s control.
  • Observability: traces of every decision, call, result, token count and termination reason.

The design rule: deterministic invariants belong in code. Writing “never call more than 20 tools” in a prompt makes a hard rule probabilistic and wastes context.

staffdesignAI RE Design the harness for a coding agent that works in a developer’s repository and can run shell commands.

Tools. Search (grep, glob), read with line ranges, edit by exact string replacement or patch (cheaper and safer than whole-file rewrites), shell, and a way to run tests. Tool output is bounded; large output goes to a file the agent can page through.

Sandbox. Run commands in a container, VM or OS-level sandbox: file writes limited to the workspace, network denied by default with an allowlist (package registries), no ambient credentials in the environment. State which capability sits inside which boundary; an external MCP tool is not covered by the shell sandbox.

Permissions. Rules evaluated in code per action: reads allowed; workspace edits allowed or ask-once; shell commands matched against allow, ask and deny patterns; pushing, deploying, deleting outside the workspace and anything touching secrets needs explicit approval. The effective action set is the intersection of sandbox, rules and approval policy.

Context. Load a repository instruction file and a compact environment description; never load the repo wholesale, search on demand. Keep the prefix stable for caching (fixed tool order, append-only history). Compact when near the limit, preserving the task, user constraints, files touched, failing tests and attempted fixes.

Feedback and verification. Compilers, type checkers, linters and tests are the dense signal that makes coding agents work; run them after edits and before claiming done. Show the diff to the user.

State. Append-only event log to replay or resume a session; file snapshots or commits as checkpoints so any step can be rolled back; explicit interrupt semantics (what happens to an in-flight command).

Extras. Read-only sub-agents for wide searches; hooks before and after tool calls for policy and formatting; full traces with token and cost accounting.

Evaluation. Repository tasks graded by hidden tests in fresh containers, plus tasks from your own codebase; report resolve rate, cost and time per task, and human intervention rate.

Threats. Injection via repository files, issue text, web pages and dependency docs; data exfiltration through the network; destructive commands. The sandbox bounds the blast radius when the prompt-level defences fail.

  • Why edit by string replacement instead of rewriting files?
  • How would you let the agent work unattended overnight without widening the risk?
  • A post-tool hook finds a secret in the diff. What can it still prevent?
seniortrade-offAI What do LangGraph, LlamaIndex, DSPy and vendor agent SDKs actually give you, and when would you write the loop yourself?

What each provides (APIs change quickly, so treat details as version-specific):

  • LangGraph: a graph or state-machine runtime. Nodes are steps, edges are transitions, a typed shared state flows through; checkpointing gives persistence, resume and human-in-the-loop interrupts.
  • LlamaIndex: a data framework for RAG: loaders, parsers and chunkers, indices, retrievers, rerankers and query engines, plus agent and workflow abstractions on top.
  • DSPy: programs written as typed signatures and modules instead of prompt strings; optimizers search instructions and few-shot demonstrations against a metric and a training set. It needs a metric and data to be useful.
  • Vendor agent SDKs (OpenAI Agents SDK, Claude Agent SDK, Google ADK and similar): a maintained loop with tool definitions, hand-offs or sub-agents, guardrail hooks, sessions and tracing, tuned for that vendor’s models.

The core loop is about 50 lines. The hard parts are tool design, context assembly, evals and permissions, and no framework does those for you.

Write it yourself when you need full control of the exact request sent to the model, when the abstraction hides prompts or token usage, or when the control flow is unusual. Use a framework for the commodity runtime you would otherwise rebuild: durable state and resume, streaming, tracing, connectors.

A practical test: can you print the exact messages and tool definitions for any call, and can you swap one component without rewriting the rest? If not, the framework will cost more in debugging than it saves.

staffconceptAI An agent run can take hours and includes a step that needs human approval. How do you make it survive crashes, restarts and a two-day wait?

Model the run as a resumable state machine, not a blocking function call.

Event log as source of truth. Append every model response, tool call, tool result, approval and error to durable storage. State is rebuilt by replaying the log; derived UI state is a projection, not a second source of truth.

Checkpoint boundaries. Persist the model’s response before executing its tool calls, and each tool result as soon as it returns. On restart, completed steps are read from the log and not re-executed.

The ambiguous step. A crash between “tool started” and “result recorded” leaves a side effect in an unknown state. Handle it with an idempotency key derived from (run id, step, call id) that the downstream system deduplicates on, or by querying the target’s state before retrying. Without one of these, at-least-once execution means duplicate refunds.

Durable approval. A pending approval is a persisted record, not a waiting process: store the exact proposed action, release compute, resume on an external signal. Bind the approval to a hash of the arguments so any change needs re-approval; give it an expiry and a defined behaviour on timeout and on rejection (the model is told and can replan).

Interruption. Define what cancel means for the model stream, the in-flight tool, effects already applied and the next resume. Killing the process is not a design.

Implementation. A durable-execution engine (Temporal-style) fits: orchestration code is deterministic and replayable, while model calls and tools are activities whose recorded results are replayed rather than recomputed. LangGraph-style checkpointers give a lighter version of the same idea.

Follow-ups

  • Why can you not simply re-run the model call during replay?
  • The context has been compacted since the checkpoint. What do you restore?

coreconceptMLE AI What does a production-grade client for a hosted model API need to handle?
  • Rate limits. Providers limit requests and tokens per minute, often separately for input and output. Handle 429 with the retry-after header; add a client-side token bucket and a queue with backpressure so bursts wait instead of failing; give interactive traffic priority over batch.
  • Retries. Exponential backoff with jitter for 429, 5xx, timeouts and overload errors, with a cap on attempts and total time. Do not retry 4xx validation errors. A retried request may be billed twice and returns a different sample.
  • Timeouts and streaming. Long generations need streaming to avoid idle-connection timeouts. Handle errors that arrive mid-stream and decide what to do with partial output.
  • Finish reasons. Check why generation stopped before using the output: natural end, token limit (truncated), tool call, or refusal or content filter.
  • Fallbacks. A secondary model, region or provider behind a circuit breaker. Prompts and tool-call behaviour are not portable across models, so the fallback path needs its own prompt tuning and its own eval results.
  • Capacity. Know your quota against peak tokens per minute; consider provisioned throughput for latency-sensitive paths; hedge requests only where tail latency justifies the cost.
  • Observability. Log request id, model version, token counts including cached tokens, latency, finish reason and retries for every call.
  • Data terms. Retention, training use, residency, and what may be sent at all.
  • Versioning. Pin dated model versions and track deprecation dates.

Follow-ups

  • You are at the token-per-minute limit at peak. What are your options?
  • What can go wrong when failing over to another provider mid-conversation?
seniortrade-offMLE AI RE LLM outputs are non-deterministic and the models behind an API change. How do you build a reliable system on that?

Where the variance comes from. Sampling (temperature, top-p). Even at temperature 0, outputs can differ between calls: floating-point results depend on batching and hardware, requests land on different replicas, and providers update serving stacks. Seed parameters are best effort. Some reasoning models do not expose sampling parameters at all.

Consequences for testing.

  • Assert properties, not exact strings: schema validity, required facts present, a grader’s verdict.
  • Run each eval case several times and report a pass rate with a confidence interval; a case that passes four times in five is a finding in itself.
  • Use record-and-replay of model responses for unit tests of the surrounding code.

Consequences for design.

  • Put anything that must be exact in code: arithmetic, lookups, permission checks.
  • Validate outputs and retry within bounds; make downstream actions idempotent.
  • Use multiple samples with voting only where the accuracy gain justifies the cost.

Model changes.

  • Pin dated snapshots; moving aliases change behaviour without a deploy on your side.
  • Snapshots are deprecated on a schedule, so migration is recurring work. Keep an eval suite that re-qualifies a new model, and expect to re-tune prompts: instructions that compensated for the old model can hurt the new one.
  • Roll out with shadow traffic or a canary, comparing quality, latency and cost.
  • Keep periodic canary prompts in production to detect upstream drift.

The goal is system-level reliability from an unreliable component, the same way distributed systems treat networks.

Follow-ups

  • A test passes locally and fails in CI one time in ten. What do you do?
  • How do you decide the number of trials per eval case?

coreconceptMLE AI RE What goes into the context window of a production LLM feature, and how do you order it?

Context engineering is choosing the smallest set of high-signal tokens that makes the next output correct. The layers:

  1. Rules: role, policies, output contract. Stable and authoritative.
  2. Tool definitions.
  3. Reference material: retrieved documents, few-shot examples.
  4. State: plan, progress, known constraints, open errors.
  5. History: recent turns and tool results.
  6. The current request.

  • Stable first, volatile last. Prompt caches match on the prefix, so tools, system prompt and fixed documents go first; timestamps, user-specific data and the question go last.

  • Say why, not just what. A short reason for a rule generalises better than emphasis.

seniorconceptMLE AI How does prompt caching work, and how does it change the way you lay out a prompt?

The provider stores the model’s computed state for a prompt prefix. A later request whose prompt starts with exactly the same tokens reuses it, so those input tokens are billed at a discount and time to first token drops.

It is a prefix match. A change at any position invalidates everything after it. So the layout is: tool definitions, then system prompt, then fixed reference material, then conversation history, then the volatile part (current question, timestamps, per-request data).

Silent invalidators.

  • A timestamp, request id or user name near the top of the system prompt.
  • Non-deterministic serialisation: unsorted JSON keys, tools listed in varying order.
  • Adding or removing a tool mid-conversation.
  • Rewriting earlier history (compaction, trimming, editing a message).
  • Switching models; caches are per model.

Provider differences (check current documentation). Some cache automatically above a minimum prefix length; others need explicit cache breakpoints. Lifetimes are short, typically minutes, extended on use. Discounts vary: on Anthropic’s API reads cost about a tenth of the base input price and writes carry a premium of about 25%, so a cached prefix pays off from the second request.

Why it matters most for agents. Each step re-sends the whole history. With an append-only history, each step pays full price only for the new tokens.

Operate it. Log cached versus uncached input tokens per request, track the hit rate, and alert when it falls; a prompt edit that drops the hit rate to zero can multiply cost with no visible behaviour change.

coretrade-offMLE AI How do you choose a chunking strategy and chunk size?

Chunk size trades retrieval precision against context. Small chunks give a focused embedding and precise matches but lose the surrounding meaning (“it increased 12%” with no subject). Large chunks keep context but dilute the embedding across several topics and spend prompt tokens on irrelevant text.

A reasonable starting point is a few hundred tokens with 10-20% overlap; treat it as a hyperparameter and tune on a retrieval eval.

Strategies:

  • Fixed size with overlap: simple baseline; splits mid-sentence and mid-table.
  • Structure-aware / recursive: split on headings, then paragraphs, then sentences; keep tables, lists and code blocks whole.
  • Semantic: split where the similarity between adjacent sentences drops.
  • Small-to-big (parent-child): index small chunks for matching, return the enclosing section to the model.
  • Contextual chunks: prepend the document title and section path, or a short model-written sentence situating the chunk, before embedding. This repairs lost referents.

Choose by document type: structured manuals and code favour structure-aware splitting; transcripts and prose favour semantic or sliding windows; FAQs are one chunk per question.

Evaluate with recall@k and nDCG on labelled queries, and end-to-end answer correctness. Looking at a few chunks is not an evaluation.

Failure modes: answers that span a boundary, split tables, overlap that returns the same text twice, and chunks so short that everything matches weakly.

seniorconceptMLE AI Why use hybrid retrieval and a reranker, and when does query rewriting help?

Hybrid. Dense retrieval matches meaning and paraphrase but is weak on exact tokens it did not learn well: product codes, error strings, rare names, new jargon. Lexical retrieval (BM25) is the opposite: exact on tokens, blind to synonyms. Their errors are complementary, so fusing them raises recall. Fuse with reciprocal rank fusion (rank-based, no score calibration needed) or a weighted sum of normalised scores.

Reranking. First-stage retrieval encodes query and document separately (a bi-encoder), which is fast but coarse. A cross-encoder reads the query and passage together and scores relevance much more accurately, at one forward pass per candidate. So retrieve 50-200 candidates cheaply and rerank to 5-10. Cost: tens to a few hundred milliseconds, depending on model size and candidate count.

Query rewriting.

  • Standalone rewrite: resolve “what about the second one?” into a self-contained query. Close to mandatory for multi-turn chat.
  • Decomposition: split a multi-hop question into sub-queries.
  • Expansion: add synonyms or generate several paraphrases and fuse the results.
  • HyDE: embed a hypothetical answer instead of the question, which moves the query closer to document space.

Rewriting costs an extra model call and can drift from the user’s intent, so keep the original query in the fusion.

Add each stage only if it moves recall@k or nDCG on a labelled set; a reranker on top of a retriever that misses the document fixes nothing.

seniorcodingMLE AI Implement hybrid retrieval with reciprocal rank fusion.

RRF scores a document by its ranks across retrievers: \(\mathrm{RRF}(d) = \sum_{r} \frac{w_r}{k + \mathrm{rank}_r(d)}\), with \(k = 60\) by convention and ranks starting at 1. A document absent from a list contributes nothing for that list.

from collections import defaultdict

def rrf(rankings, k=60, weights=None):
    """rankings: list of ranked lists of doc ids, best first. Returns [(doc_id, score)]."""
    weights = weights or [1.0] * len(rankings)
    scores = defaultdict(float)
    for w, ranking in zip(weights, rankings):
        seen = set()
        for rank, doc_id in enumerate(ranking, start=1):
            if doc_id in seen:                    # count each doc once per list
                continue
            seen.add(doc_id)
            scores[doc_id] += w / (k + rank)
    return sorted(scores.items(), key=lambda x: (-x[1], str(x[0])))   # deterministic ties

def hybrid_search(query, bm25, embed, ann, top_k=10, depth=100, flt=None):
    lexical = bm25.search(query, depth, filter=flt)           # -> [doc_id, ...]
    dense = ann.search(embed(query), depth, filter=flt)       # -> [doc_id, ...]
    return rrf([lexical, dense])[:top_k]

Pitfalls:

  • RRF uses ranks only, so it needs no score normalisation but ignores how confident each retriever was. A weighted sum of normalised scores can do better if scores are calibrated.
  • Fuse at one granularity. If one retriever returns chunks and the other documents, map both to the same id first.
  • Retrieve deeper than top_k from each list, or fusion has nothing to add.
  • Apply permission and metadata filters inside each retriever. Filtering after fusion can leave fewer than top_k results, and for permissions it is the wrong place.
  • \(k\) damps the influence of top ranks; small \(k\) makes rank 1 dominate.
  • Tune weights and depth on a labelled set; follow with a reranker if latency allows.

seniorcodingMLE AI Implement semantic chunking: split a document where the topic changes, with size limits.

Embed sentences, measure the cosine distance between neighbours, and cut at the largest jumps, subject to minimum and maximum chunk sizes.

import re
import numpy as np

def semantic_chunks(text, embed, max_tokens=400, min_tokens=80, pct=90,
                    n_tokens=lambda s: len(s.split())):
    sents = [s.strip() for s in re.split(r"(?<=[.!?])\s+", text) if s.strip()]
    if len(sents) < 2:
        return sents
    E = np.asarray(embed(sents), dtype=np.float32)                  # (n, d)
    E /= np.linalg.norm(E, axis=1, keepdims=True) + 1e-12
    dist = 1.0 - np.sum(E[:-1] * E[1:], axis=1)                     # (n-1,) neighbour distance
    thresh = np.percentile(dist, pct)                               # cut at the largest jumps
    chunks, cur, cur_len = [], [sents[0]], n_tokens(sents[0])
    for i in range(1, len(sents)):
        n = n_tokens(sents[i])
        topic_shift = dist[i - 1] > thresh and cur_len >= min_tokens
        if topic_shift or cur_len + n > max_tokens:
            chunks.append(" ".join(cur))
            cur, cur_len = [], 0
        cur.append(sents[i])
        cur_len += n
    chunks.append(" ".join(cur))
    return chunks

Pitfalls:

  • Single-sentence embeddings are noisy. Embedding a sliding window of two or three sentences around each position gives steadier boundaries.
  • The percentile threshold is relative to the document, so a single-topic document is still cut at its top 10% of jumps; the minimum size limits the damage.
  • A single sentence longer than max_tokens still needs a hard split.
  • The regex splitter breaks on abbreviations, decimals, code and tables. Split on structure (headings, tables, code blocks) first and apply this within sections.
  • Count tokens with the embedding model’s tokenizer, not whitespace.
  • Ingestion cost is one embedding per sentence.
  • Semantic chunking does not always beat structure-aware fixed-size chunking. Compare recall@k on labelled queries before adopting it.

coreconceptMLE AI RE How does function calling work, and what makes a tool definition good?

Mechanism. You send tool definitions (name, description, JSON Schema for parameters) with the request; they are rendered into the model’s context. The model either answers in text or emits a structured call (tool name plus JSON arguments). The model executes nothing: your code parses the call, runs the function and sends the result back as a tool message tied to the call id, and the model continues. Tool definitions cost input tokens on every request.

What makes a definition good.

  • Few, non-overlapping tools. Two tools that could both apply create selection errors. Prefer one task-shaped tool (get_order_status) over thin wrappers around three endpoints.
  • Descriptions written for a newcomer: what it does, when to use it, when not to, what it returns, with an example for tricky arguments.
  • Tight schemas: enums instead of free strings, required fields, explicit formats (ISO dates, ids), flat rather than deeply nested. Make invalid states hard to express.
  • Results designed for the model: compact, stable field names, ids that can be passed to the next call, pagination or truncation with a note that more exists.
  • Declared side-effect class: read, reversible write, irreversible action.

Schema-constrained (“strict”) tool calling, where the provider supports it, guarantees arguments parse and match the schema. It does not guarantee they are correct, so validate semantics and authorisation server-side.

With dozens of tools, selection accuracy drops and definitions crowd the context: namespace them, load definitions on demand through a tool-search step, or route to a subset.

seniortrade-offAI Talk me through error handling, parallel tool calls and idempotency in a tool executor.

Validation before execution. Check arguments against the schema, then semantics (ranges, existence) and authorisation (does this user own this resource). The model’s arguments are untrusted input.

Three error classes.

  • Transient (timeout, 429, 5xx): the harness retries with backoff; the model need not know unless retries are exhausted.
  • Model-fixable (bad argument, not found, precondition failed): return as a tool result saying what failed and what a valid call looks like, so the model can correct itself.
  • Fatal (auth revoked, invariant violated, policy denial): stop or escalate; do not let the model work around it.

Parallel calls. Models often emit several calls in one turn. Run them concurrently only when their effects commute: reads in parallel, writes serialised. Whether a tool is parallel-safe is metadata on the tool, decided in code. Return a result for every call, including failures, each tied to its call id.

Idempotency. A timed-out write may have succeeded. Retrying a payment, an email or a deploy can duplicate it. Options: an idempotency key per logical action that the downstream system deduplicates on; check-then-act (read current state before retrying); or a two-phase prepare-and-confirm for irreversible actions. Retried model turns can also re-propose the same action, so dedupe at the action level, not only the HTTP level.

Bounds. Per-tool timeouts, output size caps, and rate limits per run.

coreconceptAI What is the Model Context Protocol, what does it standardise, and what are its security concerns?

MCP is an open protocol, introduced by Anthropic in late 2024 and since adopted by other vendors, for connecting LLM applications to external tools and data. It turns the M x N integration problem (every app times every system) into M + N: a system exposes one MCP server, and any MCP-capable host can use it.

Architecture. A host application (IDE, chat app, agent runtime) runs MCP clients, each holding a connection to one server. Messages are JSON-RPC 2.0, with capability negotiation at initialisation.

Server primitives.

  • Tools: functions the model can call, with a name, description and JSON Schema input.
  • Resources: data the application can read into context (files, records), addressed by URI.
  • Prompts: reusable templates the user can invoke.

Clients can offer features back to servers, such as sampling (the server asks the host’s model for a completion) and roots (which directories are in scope).

Transports. stdio for local servers started as subprocesses, and Streamable HTTP for remote servers (it replaced the earlier HTTP+SSE transport). Remote authorization is based on OAuth 2.1. The specification is still evolving, so check the current revision.

Security concerns.

  • Tool descriptions and tool results are untrusted text that enters the model’s context: a malicious or compromised server can inject instructions (“tool poisoning”).
  • A server holds real credentials; over-broad scopes and token pass-through create confused-deputy problems.
  • A local stdio server runs with the user’s privileges.
  • The host’s sandbox does not automatically cover what an MCP server does.

Mitigations: allowlist servers, pin versions, least-privilege scopes, per-tool approval for writes, and treat everything returned as data.

coreconceptMLE AI RE What is prompt injection, what is indirect prompt injection, and why can you not fix it with a better system prompt?

A language model receives instructions and data in one token stream and has no reliable way to tell them apart. Prompt injection exploits this.

  • Direct injection: the user writes text that overrides the application’s instructions (“ignore the above and…”). A jailbreak is the related attack on the model’s own safety policy rather than the application’s instructions.
  • Indirect injection: the instructions are planted in content the system reads on the user’s behalf: a web page, email, document, code comment, tool result or tool description. The user is the victim, not the attacker.

A stronger system prompt or delimiters around untrusted text lowers the success rate but does not make it zero, and an attacker can retry. So assume some injections succeed and limit what a successful one can do.

The dangerous combination is an agent that has all three of: access to private data, exposure to untrusted content, and a way to send data out (web requests, email, rendering a URL or image). Remove one and exfiltration is blocked.

Defence in depth:

  • Least-privilege tools; read-only where possible.
  • Human approval for consequential or outbound actions.
  • Egress control: allowlisted domains, no auto-rendering of model-produced links or images.
  • Isolation: a quarantined model reads untrusted content and returns constrained data to a privileged one that never sees the raw text.
  • Taint tracking: once untrusted content is in context, restrict the tools available.
  • Injection classifiers on inputs and tool results, as one layer.
  • Logging and a red-team suite that measures attack success rate.

coreconceptMLE AI What determines the cost and latency of an LLM feature, and which levers do you pull first?

Cost per request is \(\text{uncached input} \times p_{in} + \text{cached input} \times p_{cache} + \text{output} \times p_{out}\). Output tokens (including reasoning tokens) are priced several times higher than input tokens on most APIs. An agent multiplies this by the number of steps, and each step re-sends the history.

Latency is roughly time to first token plus output tokens divided by generation speed. Time to first token grows with queueing and with uncached prompt length; total latency is dominated by output length.

Levers, in the order I would try them:

  1. Prompt caching: stable prefix, check the hit rate. No quality cost.
  2. Trim input: fewer and shorter retrieved passages, bounded tool outputs, compaction.
  3. Trim output: concise formats, no restating of the input, appropriate token limit, lower reasoning effort where it does not change results.
  4. Smaller model for easy steps (routing, extraction), kept honest by an eval.
  5. Batch API for offline work: asynchronous, typically about half price.
  6. Response caching for repeated queries: exact-match is safe; semantic caching risks wrong hits, staleness and leaking across users.
  7. Parallelise independent calls; stream to improve perceived latency (it does not shorten total time).

Measure cost per completed task, not per call. A cheaper model that needs more steps or more retries can cost more per task. Track tokens in and out, cached fraction, steps per task and latency percentiles per route.

stafftrade-offMLE AI Design model routing for an LLM product. When does a router or a cascade save money, and when does it backfire?

Two designs.

  • Router: a cheap classifier (or small LLM) predicts difficulty or intent and picks a model up front. One model call per request.
  • Cascade: call the small model first, and escalate to the large one when a check fails (schema or business validation, a verifier, low self-consistency, a learned confidence score).

Economics. With escalation rate \(e\), expected cascade cost is \(c_s + e \cdot c_l\) against \(c_l\) for always-large. It saves money only if \(c_s + e \cdot c_l < c_l\), that is \(e < 1 - c_s / c_l\), and the escalated requests pay both latencies. A router avoids the double call but its mistakes are silent: a hard query sent to the small model simply gets a worse answer.

How to set it up. Label a traffic sample with both models’ outputs and quality grades. Sweep the threshold and plot quality against cost; choose the operating point, and check quality per slice, not only on average, because routing errors concentrate in the hard tail that matters most.

Where it backfires.

  • LLM self-reported confidence is poorly calibrated; prefer external checks.
  • Two models means two prompts, two eval suites and two cache namespaces.
  • A provider upgrade to either model shifts the optimal threshold.
  • On multi-step agent tasks, a weaker model that takes more steps can cost more per task.

Alternatives to test first. The large model at lower reasoning effort; prompt caching; a fine-tuned or distilled small model for one narrow, high-volume task with a fallback to the large model on validation failure.

Monitor the route mix, escalation rate, per-route quality and cost per completed task.

seniordebuggingAI Your LLM bill tripled the week after a prompt change, with flat traffic. How do you find the cause?

\[ \text{cost} = \text{tasks} \times \text{calls per task} \times (\text{uncached in} \cdot p_{in} + \text{cached in} \cdot p_{cache} + \text{out} \cdot p_{out}) \]

  5. Model mix changed. A routing or fallback rule now sends more traffic to the expensive model.
  6. Not the prompt at all. A retry storm from rate limits, a batch job, or a new caller, coinciding with the change.

coreconceptMLE AI Explain HNSW, IVF and product quantization, and the recall-latency-memory trade-off each one exposes.

Exact nearest-neighbour search is \(O(Nd)\) per query. Below roughly \(10^5\) vectors that is a few milliseconds and brute force is the right answer. Beyond that, approximate indexes trade recall for speed and memory.

HNSW (graph). A multi-layer proximity graph; search starts at the sparse top layer and greedily descends. Parameters: M (links per node, typically 16-64), efConstruction (build quality), efSearch (query-time beam: higher means better recall and slower). High recall at low latency, roughly logarithmic query scaling in practice. Costs: full vectors plus links in RAM, slow builds, deletes handled by tombstones.

IVF (partitioning). k-means splits the space into nlist cells (on the order of \(\sqrt{N}\)); a query scans the nprobe closest cells. nprobe is the recall-latency knob. Less memory overhead than a graph, needs training, and degrades when the data drifts from the trained centroids.

Product quantization (compression). Split each vector into \(m\) sub-vectors and replace each with the id of its nearest of 256 centroids: \(m\) bytes per vector. A 768-dimension float32 vector is 3,072 bytes; with \(m = 96\) it is 96 bytes, 32 times smaller. Distances come from lookup tables. It is lossy, so re-score the top candidates with full vectors.

Typical combinations. HNSW when the data fits in RAM; IVF-PQ at the billion scale; disk-based graphs (DiskANN-style) when RAM is the constraint. Scalar or binary quantization with re-scoring is a simpler alternative to PQ.

Always measure. Compute recall@k against exact search on a query sample and plot it against latency; ANN recall is a property of your data and parameters, not of the library.

seniortrade-offMLE AI How does metadata filtering interact with ANN search, and when is pgvector enough versus a dedicated vector database?

Filtering. Three approaches:

  • Post-filter: run ANN, then drop non-matching results. With a selective filter (1% of rows match) a top-100 search returns about one usable result.
  • Pre-filter: select matching rows, then search exactly within them. Exact and cheap when the subset is small, linear in subset size when it is not.
  • Filter-aware index traversal: skip non-matching nodes during graph search. Good at moderate selectivity; at very low selectivity the graph of matching nodes is disconnected and recall collapses unless the engine falls back to brute force.

Good engines choose by estimated selectivity. If the filter is always a tenant id, use a partition or namespace per tenant instead of a filter.

pgvector is enough when the corpus is in the millions to low tens of millions of vectors, the index fits in memory, QPS is moderate, and you benefit from one system: joins with relational data, transactions, row-level security for permissions, existing backups and operations. These thresholds are rules of thumb and depend on dimension and hardware. Filtered ANN behaviour in pgvector is version-dependent, so test it with your real filters.

A dedicated store earns its place at hundreds of millions of vectors or more, with strict p99 latency at high QPS, heavy filtered or hybrid search, many tenants, or a need for built-in quantization, disk-based indexes and sharding.

Either way, plan for the operational events: a new embedding model means re-embedding everything and a dual-index migration; shorter dimensions (Matryoshka-style embeddings) and quantization cut memory at some recall cost.

coreconceptMLE AI How do you get reliable structured output from an LLM? What do JSON mode and schema-constrained decoding guarantee, and what do they not?

Three levels of guarantee:

  1. Prompt only (“reply in JSON with these fields”). Works most of the time; failures include prose around the JSON, trailing commas, missing fields.
  2. JSON mode. The output is syntactically valid JSON, with no guarantee about fields or types.
  3. Schema-constrained decoding (structured outputs, strict tool calling). The schema is compiled to a grammar, and at each step tokens that would violate it are masked. Output that completes always parses and matches the schema.

What constrained decoding does not guarantee:

  • Completion. Hitting the output token limit leaves truncated JSON; check the finish reason.
  • Correct values. A date field holds a valid date, not necessarily the right one.
  • Full JSON Schema. Providers support a subset (limits on recursion, numeric and string constraints, optional fields); check the documentation.
  • No refusal. The model may still decline.

Schema design matters as much as the mechanism:

  • Generation is left to right, so put reasoning or evidence fields before the verdict; forcing the answer first removes the model’s chance to think.
  • Allow null or “unknown” so the model is not forced to invent a value.
  • Use enums for categories; keep nesting shallow; describe each field.
  • For extraction, ask for the supporting quote alongside the value so it can be verified.

Then validate anyway (types with Pydantic or JSON Schema, plus business rules such as totals that must add up), and retry with the validation error on failure.

from pydantic import BaseModel, ValidationError

def extract_json(text: str) -> str:
    start, end = text.find("{"), text.rfind("}")
    if start == -1 or end <= start:
        raise ValueError("no JSON object found in output")
    return text[start:end + 1]

def structured_call(llm, messages, schema: type[BaseModel], max_attempts=3, check=None):
    """llm(messages) -> str. Returns a validated `schema` instance or raises."""
    msgs, last_err = list(messages), None
    for attempt in range(1, max_attempts + 1):
        raw = llm(msgs)
        try:
            obj = schema.model_validate_json(extract_json(raw))
            if check is not None:
                check(obj)                       # business rules; raises ValueError
            return obj
        except (ValidationError, ValueError) as e:
            last_err = e
            msgs = list(messages) + [            # keep only the latest failed attempt
                {"role": "assistant", "content": raw},
                {"role": "user", "content":
                    f"That output was invalid:\n{e}\n"
                    "Return only a corrected JSON object that matches the schema."},
            ]
    raise RuntimeError(f"no valid output after {max_attempts} attempts: {last_err}")

Pitfalls an interviewer checks:

  • Bounded attempts. Each retry is a full paid call; two or three is the usual cap.
  • Feed back the specific error, not “try again”. The validator’s message tells the model which field to fix.
  • Do not accumulate every failed attempt in the history; it grows cost and anchors the model on its mistakes.
  • Separate transport errors (429, 5xx, timeouts) from validation errors; they need backoff, not a repair prompt.
  • Semantic checks belong in check: cross-field consistency, values present in the source text.
  • No side effects before validation succeeds.
  • Log the attempt count. A rising retry rate is an early signal of a prompt or model regression.
  • With schema-constrained decoding the wrapper is still needed for truncation, refusals and business rules.

Extensions: escalate to a stronger model on the last attempt; return a typed failure instead of raising so the caller can route to human review.

seniordesignAI RE Design a real-time voice agent. Where does the latency go, and how do you handle turn-taking and interruptions?

Pipeline. The cascaded design is voice activity and turn detection, streaming speech recognition, the LLM, then streaming text-to-speech. The alternative is a speech-to-speech model that consumes and emits audio directly.

Latency budget. People expect a reply within a few hundred milliseconds of finishing; beyond about a second the conversation feels broken. Typical contributions (approximate, system-dependent): end-of-turn detection 200-500 ms, final transcript 100-300 ms with streaming ASR, LLM time to first token 200-500 ms, TTS time to first audio 100-300 ms, plus network. What matters is time to first audio, not total generation time.

Reducing it. Stream every stage; start TTS on the first clause rather than the full reply; use a fast model and a short, cached prompt; co-locate services; replace a fixed silence timeout with a turn-detection model that uses what was said; speak a short acknowledgement before slow tool calls.

Turn-taking and barge-in. When the user starts speaking during playback: stop audio immediately, cancel the in-flight LLM and TTS, and truncate the stored assistant turn to what was actually spoken (this needs TTS timing information), otherwise the model believes it said things the user never heard. Echo cancellation stops the agent from interrupting itself. Short back-channels (“mm-hm”) should not count as interruptions.

Cascaded versus speech-to-speech. Cascaded gives text at every stage, so guardrails, tool calling, logging and model choice are straightforward, but it loses prosody and adds latency. Speech-to-speech is faster and more natural, and harder to inspect and control.

seniorconceptAI RE How would you design memory for an agent that works with the same user across many sessions?

Separate three things:

  • Working context: what is in the window now.
  • Session state: the conversation, plan, scratchpad and checkpoints for one task.
  • Long-term memory: what persists across sessions. Useful sub-types are semantic (facts and preferences), episodic (what happened in past sessions) and procedural (instructions and learned ways of working).

Write path. Decide who writes (the agent through an explicit tool, or a background extraction job after the session), what is written (distilled statements with a timestamp and provenance, not raw transcripts), and how conflicts resolve (a new fact supersedes or updates the old one rather than accumulating). Add expiry for things that go stale.

Read path. A small, always-loaded profile for things that matter every time; everything else retrieved on demand by search, or kept as files the agent lists and reads. Always-loaded memory costs tokens on every request and can break prompt caching if it changes often.

Failure modes.

  • Stale or wrong memory: an error written once is replayed forever. Keep provenance, let the agent verify against the current state, and prefer current observations over memory.
  • Poisoning: injected content written to memory persists across sessions and survives the end of the attack. Do not write memory from untrusted content without review.
  • Bloat: retrieval returns marginally relevant memories that distract.
  • Privacy: scope strictly by user and tenant; let users inspect and delete.

Evaluate with multi-session tasks where the answer depends on an earlier session, and measure both recall of needed memories and the rate of wrong-memory use.

Start simple: a structured profile plus notes files beats a vector store until volume demands one.
